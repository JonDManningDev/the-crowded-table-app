# Persistent TypeScript API transition proposal

**Approved 2026-11-03.** The owner approved the proposed stack, role model, archive RLS, package revision and local pilot sequence. The sections below preserve the reviewed rationale. Implementation evidence is tracked in [12](12-implementation-status.md).

**Recommendation.** Keep the current frontend feature APIs as the point of change. Move one working feature, Account Settings, through a Fastify service to PostgreSQL. Prove identity, audit attribution, browser lockout and recovery there. Then migrate community creation and its dependent lifecycle operations as a coordinated unit. Revise Packages 2–3 **before executing Package 4**. Implementing the proposed PostgREST projections, permission helpers and public RPCs first would create a second authorization system just as the application starts to use the first one.

## 2. Service and responsibility boundaries

| Owner | Proposed responsibility | Boundary |
| --- | --- | --- |
| Browser | Keep Supabase Auth and current feature adapters. Send bearer token, selector, typed input and stale-state token where applicable. Render only the returned model. | No privileged key, raw DB type as a public contract, arbitrary query expression or client assertion of authority. |
| Supabase Auth | Issue and refresh sessions, confirm identity, manage credentials, recovery and bans. | Community authority and account standing come from current application state. |
| API | Authenticate requests, construct actor context, evaluate operation-specific product rules, shape audience-specific results, coordinate transactions and map errors. | Every route has an explicit anonymous or authenticated contract. Repositories require the authorized query scope or transaction from the service. |
| PostgreSQL | Authoritative records, migrations, keys, constraints, indexes, defaults, atomic commit, protected audit writes and narrowly justified row guards. | Dedicated non-owner runtime principal. Keep the G-02 archive fence. Enforce hard stored-state invariants even when two workflows interleave. |
| Storage / Realtime / workers | Introduce only with a real feature. Issue scoped object access after checking resource audience, define revocation/expiry, authorize subscriptions and payloads separately. Deliver committed side effects via an outbox when a feature needs reliable delivery. | A signed URL, changefeed, broadcast, old subscription or retained attachment can disclose data outside HTTP. Deny unreviewed paths and verify each retained surface before its first records. |

**Stack choice.** Use a single Node service with Fastify. Its route request and response schemas suit the project's field-by-field access contracts, and plugin scopes can group routes by feature. Hono is a credible alternative with a Node adapter and Web Standard interfaces. Portability across edge runtimes offers little advantage for this persistent PostgreSQL service. Prefer Fastify's existing schema/serialization and injection-testing conventions. Use TypeBox and its matching Fastify type provider as the schema source for runtime validation and transport types. AJV validates requests and Fastify serializes responses from the emitted JSON Schema. Explicitly reject extra input fields, including mixed allowed/forbidden patches, instead of relying on validator defaults that can strip them. Use explicit output projections and response schemas. Test actual serialized bodies. [TypeBox decision](08-decisions-and-open-questions.md#typebox-for-fastify-http-schemas--accepted-direction-2026-11-09) · [Fastify schemas](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/) · [Hono on Node](https://hono.dev/docs/getting-started/nodejs)

**Database access.** Recommend Kysely with the PostgreSQL dialect and `pg`. Typed joins, explicit projections, conditional updates and visible SQL match a schema with composite tenant keys, audit triggers and reviewed SQL migrations. Use bound raw SQL where locking or a PostgreSQL feature benefits from it. Plain parameterized `pg` is viable but requires more manual mapping for these projections. Drizzle also supports SQL-like queries and transactions. Its TypeScript schema model adds a second schema description to reconcile with the existing migration-first workflow. Use one migration authority. Generate server query types from the locally replayed schema, verify drift in CI, and explicitly map dates/nullability and insertable/generated fields. Share HTTP contracts independently of either database type generator. [Kysely](https://kysely.dev/) · [Drizzle](https://orm.drizzle.team/docs/overview) · [node-postgres transactions](https://node-postgres.com/features/transactions)

**Module layout.** Add a sibling `server/` package and a small shared HTTP-contracts entry in the same repository when approved. Keep the Vite app in place. Server startup owns config, logger, connection pool and route registration. A request hook verifies the token. A handler parses the input and calls a named feature service. The service owns the read scope or transaction. Feature query functions take a database/transaction handle and return fixed projections. Start with accounts and communities. Put common verified-actor, standing, effective-staff and owner predicates in a small authorization module. Keep audience rules that only profiles, discipline or activities understand next to that feature. Pass explicit dependencies. A handler can call a simple read directly through an authorized query function. Avoid a repository class per table, a generic CRUD endpoint or a dependency-injection container.

**HTTP and operations.** Use same-origin `/api` forwarding where available, otherwise an explicit origin allowlist. Validate body, path, query, page limits and cursors. CORS affords no authorization. Use stable domain error codes and a request ID. Respond with 401 for invalid identity, 403 for known forbidden operations, indistinguishable 404 outcomes for hidden or absent targets, and 409 for a stale transition or uniqueness conflict when the caller can know it. Enforce bounds and rate limits on public lookup, discovery and mutations. Redact tokens, private content, request bodies and credentials from logs. Keep private results out of shared/PWA caches and discard user-scoped client state on session change.

**Connections and hosting.** Build one portable Node process/container listening on an injected port, with TLS, secrets supplied at runtime, health/readiness probes and graceful request/pool drain. Start near the supplied us-west-2 database region. Use one bounded `pg.Pool` per process via direct TLS with certificate verification where IPv6 or the project network supports it. Prefer Supavisor session mode for IPv4-only hosting. Transaction pooling needs a separate compatibility test for prepared statements and connection-local state. Budget pool size × maximum replicas, including rolling overlap, below the available database slots after reserving Auth, operations and migrations. Set acquisition, statement, idle-transaction and lock timeouts. Measure HTTP latency, pool wait, transaction duration, deadlocks, denials and error rates. Select a host after confirming regional latency, network family, persistent-process cost and connection limits. [Supabase connection modes](https://supabase.com/docs/guides/database/connecting-to-postgres)

## 3. Authorization from request to commit

1. **Establish identity.** Accept anonymous access only on named public operations. A supplied invalid token fails authentication. Validate the access token against the configured project's issuer, audience, expiration, allowed algorithm and subject format. For asymmetric signing, use a maintained verifier with the project's fixed JWKS address, bounded cache and rotation handling. With legacy symmetric signing, validate through Supabase Auth's user endpoint and keep signing secrets out of the service. Reject anonymous identities and non-user credentials for verified-user operations. Browser `getSession()` supplies a token, never proof. [Supabase JWT verification](https://supabase.com/docs/guides/auth/jwts)
2. **Establish eligibility.** Request context carries the verified subject and a server-generated request ID. For protected operations recheck current confirmed/non-null email, non-anonymous identity, lack of an active ban and required application account. Use a narrow private database accessor with a fixed search path, minimal owner privileges and runtime-only execution for Auth facts. Expose only eligibility, never raw Auth rows or failure reasons to staff. Scope candidate checks to an authorized candidate query. A still-valid token from a now-banned actor fails. Preserve AM-06's distinct applicant rule: a target Auth ban alone neither removes a request nor prevents an otherwise valid approval. Global deactivation is a separate future workflow.
3. **Resolve selectors.** Derive self from the actor. Resolve tenant, target and source keys against stored relationships, carrying composite tenant keys through joins and updates. A resource under a mismatching tenant yields no accessible record. Never use a route slug, target ID, badge, JWT user metadata, browser preview role or body permission flag to establish entitlement. Load only the facts required for that operation. UI capability hints expire with the response.
4. **Apply the correct audience in SQL.** Build named query predicates for the eligible dataset and use them inside the query, before count, ordering, cursor and pagination. One exact-target lookup can have broader access than search. Multi-step reads requiring a consistent view use a single statement or a single appropriate snapshot. Recheck on the next fetch or delivery. Avoid fetching all rows and filtering in JavaScript, and avoid one permission query per row.
5. **Authorize and write in the same transaction.** A service starts one transaction on one checked-out connection, binds trusted actor context, locks the relevant shared roots, loads facts, evaluates the typed decision, performs conditional writes with expected state/revision and checks affected rows. Commit correlated audit records and any outbox records together. On any failure roll back all changes. Never call an external service or send a notification while holding the transaction open.

| Reusable rule | Operation-specific composition and nearest denial |
| --- | --- |
| Effective staff and ownership | Effective staff needs an active assignment, approved account in the same tenant and the required flag. Ordinary operation also needs an active tenant. A distinct owner check protects owner targets and permits only documented archived management. Giving every flag to an admin never makes that person the owner. `can_grant_staff` delegates only the two audit flags for permission editing. Reject a whole mixed patch. |
| Standing and discipline | Pending can manage its own onboarding profile. Suspended retains approved public visibility, own profile and independently eligible private activity/DM access. New community-public creation/reservations are barred. Suspending/removing an active or paused staff target needs both discipline flags and linked staff revocation. Owner immune. Never-approved pending may be removed, never suspended. Clearance restores a suspended member to approved, leaves inactive inactive and closes a pending restricted-return request. No automatic staff restoration. |
| Profile audiences | Global search requires discoverability and excludes bilateral blocks. Opening one target may instead use qualified sharing in a shared active community or encounter in a real authorized app-wide source. Validate viewer, target and source together. A community activity alone gives no global grant. Community profiles follow their own mandatory member rules even across a personal block. Eligible viewers can open an inactive target by exact tenant and target, never enumerate former members. Under G-05b the source feature authorizes its own record once. Archived community-account content additionally requires the owner, including self reads. Private preferences stay self-only. |
| Public and historical reads | Exact active slug may return the seven landing fields, public settings and seven supported copy overrides projected to three fields. No community list. Within one known active community with directory enabled, return eligible display names and effective badges only. Activity and chat visibility flags are independent. A relationship card, historical message identity, private label, audit event link or report evidence confers only its own audience. |
| Blocks, communications and resources | Directed block records have bilateral effects. Either direction denies full global profiles and new direct contact. Apply accepted upcoming private host/participant effects, preserve independent guests and in-progress participation. Competitive blocks affect communication, preserve entries/results/pairings. Resource features supply their own participation, hosting, capacity and lifecycle checks. Keep global vs community consent, invitations, live access and retained history separate. Owning the block row confers no right to clear the other direction. |

**Worked command — approve a join.** The handler accepts tenant ID, request ID and expected revision. Resolve the actor from the token. In the transaction lock the tenant first, then actor and target account rows in stable key order and the involved assignment/request. Re-read tenant status, actor eligibility, approved standing, active assignment and `can_approve_users`. Match the exact current join request, target, kind and revision, and check pending unrestricted standing. Set first approval once, consume that request and record the event. A withdrawal followed by reapplication has a different UUID. The old request cannot apply to it. A discipline-only queue reader can see restricted returns but cannot approve a join. An Auth ban of the applicant does not alter this test. [Queue and command contracts](19-access-migration-specification.md#transactional-command-contracts)

**Concurrency contract.** All writers of a changing authorization fact must coordinate on the same lock or comparable serializable predicate, including revocation, archive, block, deactivation and admission. A lock on a missing request/block row protects nothing. Lock stable parent accounts/identity pairs and enforce unique constraints on dependent rows. Specify a total order before enabling a cross-domain writer, including multi-tenant/global operations. Re-read eligible state after locks at READ COMMITTED, or retry the entire transaction on serialization failure under SERIALIZABLE. Resolve Auth-eligibility races for sensitive commands using a narrowly privileged guard that coordinates with updates to the actor's Auth row, or a synchronously maintained eligibility row with the same locking contract. Prove ban-vs-command ordering before enabling those commands. Limit retries for serialization/deadlock failures, rebuilding all decisions with fresh facts. For uncertain commits use a unique operation key scoped to actor and action, validate the request fingerprint and authorized replay result. Never blindly replay non-idempotent POSTs. Enforce the cross-row inactive ⇒ sharing false invariant even on concurrent preference changes. Compare both commit orders in tests.

## 4. Database authority, attribution and migration inventory

**Runtime principal.** Use a dedicated login such as `ct_api`, distinct from deployment, Auth provisioning and background work. It owns no application objects, has no superuser, BYPASSRLS, DDL, role-administration, TRUNCATE, trigger-disable or role-switch path to elevated roles. Grant CONNECT, selected schema USAGE, named SELECT/column DML and signature-specific private EXECUTE per shipped feature. Restrict schema CREATE, schema search paths and public function EXECUTE. Keep the migration/owner credential out of runtime and out of browser builds. Inventory inherited and PUBLIC rights as well as explicit grants. Use parameterized SQL with allowlisted identifiers. The runtime is trusted to implement the API's authorized application operations. Its compromise could impersonate actors within its granted surface. Audit context alone cannot defend against a compromised trusted writer.

**RLS mechanics.** A direct `pg` connection to an RLS table has no PostgREST-supplied `auth.uid()`. Current policies target `authenticated`, so a distinct runtime role with SELECT but no applicable policy gets default-deny. For each slice define a role-specific permit policy bounded to the intended operation: self-only for the preferences pilot, and minimal server access for query orchestration elsewhere. On community-account content keep G-02 as an independently enforced restrictive owner-or-active predicate combined with applicable permissive policies. It must fail closed on absent actor context and avoid recursive policy joins. Use an unexposed, tightly granted helper for a protected ownership fact where necessary. Apply archive restrictions to account/profile and related content per document 19, test self/private-preference exceptions separately, and preserve fixed projections such as personal summaries via an individually reviewed narrow read function if the guard would hide their legitimate inputs. Do not grant raw archived rows to make a card render. For API-only relations evaluate retaining cheap self/tenant fences against their actual query needs. Never create a general-purpose owner/definer read escape hatch. [Archive decision](19-access-migration-specification.md#archive-enforcement-decision) · [PostgreSQL row security](https://www.postgresql.org/docs/17/ddl-rowsecurity.html)

**Actor propagation.** On one transaction-bound connection, set a transaction-local actor UUID from the verified subject using parameterized `set_config(..., true)` before protected SQL. Bind the server-generated operation ID the same way. Wrap protected reads that depend on this context in a transaction too. A private accessor selects the identity source by trusted login/path: runtime requires the bound actor, legacy PostgREST uses its verified JWT context while it remains, Auth provisioning uses the new Auth identity under its restricted trigger path. Reject missing, malformed or ineligible runtime actors. Never accept attribution fields from payloads, use a connection-wide SET, or silently coalesce to a system identity. Use explicit, separately privileged provenance for migration or system events. Test commit, rollback, exceptions, anonymous reads and next-user reuse with a one-connection pool. Validate login/role detection with the chosen pooler, including inside definer functions where `current_user` changes. A custom PostgreSQL setting is a trusted-service assertion, not an independent signature. A browser-callable setter, privileged RPC that accepts arbitrary actor IDs, or client SQL execution would break this design.

**Audit integrity.** Let SQL preserve original creation fields, stamp actor/time, validate event shapes and enforce immutable rows/categories. Give the runtime no direct UPDATE/DELETE/TRUNCATE or unrestricted INSERT to the audit tables. For sensitive workflows, keep a small private mutation or trigger-backed event recorder where necessary to enforce that a protected transition cannot commit without its required semantic event. Derive before/after from actual changes, validate event/operation/tenant linkage, and avoid recording both a generic and semantic event for the same change. In a staff suspension the community event owns the reason. Link active→revoked as a separate event in both histories. Paused→revoked is staff history only. Authorize every event link independently. Preserve historical actor/time and only evidenced legacy categories. A generic legacy update does not prove a particular transition. Never put private conversation contents in audit details. [G-04 rules](19-access-migration-specification.md#structured-actions-and-history)
