Status: **current canonical client architecture direction**, recorded from the user's architecture decisions on 2026-10-02. Required stack: Vite, TypeScript, React Compiler. This guides the upcoming prototype refactor; it is reviewable and may evolve as real requirements emerge. Updated 2026-10-03 for personal/community scope and 2026-10-12 for the planned table guest-management interaction.

This document owns client boundaries, data/state, and styling decisions. The [file structure plan](07-file-structure.md) owns illustrative paths, migration steps, and the current-code conflict inventory. The [decision register](08-decisions-and-open-questions.md#client-architecture-review-questions) tracks questions to revisit. Neither document requires the target structure to exist immediately.

Current product scope (2026-10-12): payments and paid memberships are late-stage work. Current feature flows must have no member/guest payment previews, paywalls, pricing/checkout, payment verification, or entitlement-dependent behavior. Remove the legacy prototype simulations during the domain refactor rather than carrying them into the new client. Community approval, private audiences, and resource authorization still apply.

## Decisions made

- Use a pragmatic feature-oriented / vertical-slice architecture. Keep code that changes together close together; most application behavior belongs to business capabilities under `features`.
- Keep startup, providers, routing, navigation, shell/layout, and cross-feature page composition under `app`. Feature-owned route pages belong in that feature's `pages` directory. Keep `App.tsx` small.
- Use `components/primitives` for generic visual building blocks and `components/shared` only for genuinely cross-feature Crowded Table visual concepts. Domain-specific components otherwise stay with their feature.
- Use `lib` for reusable technical infrastructure. Feature UI should not directly depend on Supabase; feature data access owns backend calls.
- Plan for TanStack Query to manage server state. Local React state handles ordinary transient UI state; do not introduce Redux by default. TanStack Query is the intended direction, not an already-installed dependency.
- Prefer feature-local types; generated Supabase schema types belong with Supabase infrastructure. Database rows and UI models need not remain identical.
- Use colocated CSS Modules as the default component styling mechanism, with semantic CSS custom properties for design tokens and controlled community theme presets. Do not accept arbitrary tenant-provided CSS.
- Configure or retain `@` as the `src` alias when refactoring imports. Use abstractions and directories only when actual code or a concrete requirement justifies them.

## Recommended ownership and dependency conventions

A feature represents a business capability, not a screen or visual variation. Likely owners are auth, user accounts (global account/profile behavior), events, Meet & Play, championships, communities (creation/management, associations, and curated community profiles), discussion (community social content), and games. D-111 replaces the earlier single `profile` feature suggestion with explicit global/community ownership. Learn & Play, RPG One-Shot, Social Game Night, Halloween Game Night, and Murder Mystery should remain event types/configurations when they use the same underlying Events capability.

If a route primarily exposes one domain capability, its page belongs to that feature. Keep route-level composition recognizable under `pages`, separate from ordinary components. The application router imports those pages. The account page lives at `features/user-accounts/pages/UserAccountPage.tsx`; My Home and My Communities are tab components under `features/user-accounts/components`, per the 2026-10-20 cleanup decision. Community Home is a separate composition scoped to the browsed community (eventually `app/pages/CommunityHomePage`); its current mock remains `features/Home.tsx`. Community creation/management and community profiles belong to `communities`, global account/profile behavior to `user-accounts`, social content to `discussion`, and authentication/session behavior to `auth`. The current `Community.tsx` is a legacy filename, not the future owner of all community capabilities.

### Global and community profile forms — accepted target 2026-10-15

Both profile types initially expose `display_name` and optional `bio`. The community join UI loads the caller's own global profile through the user-account feature's contract and pre-fills an editable community draft. Preserve edits during refetch/retry; once initialized, new global data must not silently replace the draft. If no global profile exists, allow direct entry, requiring a nonblank name and permitting an empty bio. Show clearly that this introduction is for the selected community.

Submit the community profile and join request through one transactional command. Do not create the account and then save its profile in a second client call. Apply the same fields and atomic behavior to optional participation in community creation. Failed requests retain the draft, and success reflects committed account/profile state. Existing-account reactivation/reinstatement is not a new join or a way to overwrite a saved profile. Later global/community edits are independent; an empty community bio stays empty rather than inheriting global text.

The community Profile destination continues to show the curated community presentation and authorized local activity. A global profile editor belongs in the personal account area; its navigation is My Account → Overview (`/account`). Distinguish global and community profile query keys, and include the viewer and relevant community/audience context for restricted projections. Never reuse an owner's full self-profile response as another viewer's permitted projection. Apply access/preference changes to caches and subscriptions when their policy ships.

Present three separate self-controlled settings with the accepted defaults: community `show_global_profile` false, global account `user_is_discoverable` true for standard global search, and global account `enable_matchmaking` true for global matchmaking. Place the first in community-account settings and the latter two in personal account settings. Explain their independent purposes; do not make search opt-out disable community profile visibility or matchmaking, or make matchmaking opt-out disable search. Use persisted values rather than reapplying defaults when reopening a form or joining another community. None is a contact permission.

D-115 selects account-level blocking and private labels without a public identification code. Show the viewer's own label alongside an otherwise authorized encountered account, independent of its current display name or global-profile visibility. Label editing is separate from blocking; keep labels out of public cards, subject-visible data, staff views, and notifications. Clear private label/profile data on sign-out or account changes, and partition caches by the viewer. Existing personal DM blocks remain tied to the underlying main account. Q-016 retains label UI/text limits and remaining audience/lifecycle details, not the selection of this mechanism or the preference names/defaults.

D-116 removes the blocked pair from each other's global search/match results and disables direct invitations in both directions. Clear affected cached candidates when block state changes and handle server rejection if a block changes after rendering. D-118 denies private event/table admission when the actual host and participant have a block in either direction, and automatically removes existing counterpart participation/rejects related invitations at block confirmation for not-yet-started resources under D-119. Guests remain independently eligible and in-progress gatherings retain existing participation/access. Community joining and unaffected shared/non-private participation remain available under normal rules; do not promise complete separation. A private label may help the viewer recognize an otherwise visible account without publishing block relationships.

### Block confirmation with existing items — accepted target 2026-10-15

D-117–D-119 require the block confirmation to distinguish automatic private consequences from optional non-private actions, limited to not-yet-started resources, all within the same interface. Show safe resource/community, time, status, relationship, and dependent effects. Explicitly list (1) private events/tables hosted by the target that the caller will automatically leave, including invitations that will be rejected, and (2) private events/tables hosted by the caller from which the target will automatically be removed, with corresponding invitation rejections. Include pending requests and confirmed participation for those upcoming gatherings. Explain that the sponsor's guests remain independently eligible and that in-progress events/tables are unaffected; exclude both from cancellation selections. These consequences have no Keep toggle; confirming the block accepts them.

Only not-yet-started non-private resources and their invitations receive manual per-item withdraw/cancel/deny/decline/revoke controls, subject to the caller's existing authority. Start these optional choices unselected. The caller can choose no manual changes, but mandatory private effects still apply. A third-party co-attendee gains no right to remove the target; unaffected shared third-party private gatherings have no manual cancellation control in this block interface. Cancel/dismiss discards the draft without blocking or changing records. Do not cancel entire gatherings, the account holder's guests, other guests, or peers implicitly.

Show cascades before confirmation: automatic withdrawal from a private event also clears the affected attendee's linked not-yet-started table seats, even if a child table is non-private. Those dependent removals are mandatory, not optional non-private choices. Preserve guest seats and any in-progress participation with its required registration/access. Use a server-derived preview, refresh material scope/permission changes and exclude gatherings that have started before reconfirmation, and retain the dialog/optional choices after errors. Confirmed outcomes remain visible in place. Unselected non-private items, independent guests, and in-progress/unaffected shared participation retain normal rules; removed private participation/invitations do not reappear when unblocked.

### Feature dependencies

The general dependency direction is:

```text
main.tsx → app (App/providers/router/layout) → feature pages
         → feature components/hooks → feature API/data access
         → lib infrastructure → external services
```

This describes ownership, not a requirement that every operation traverse every layer. Generic primitives can be consumed throughout the upper UI layers. Features should not depend upward on application composition; `lib` and primitives should not depend on business features. Avoid circular feature dependencies. Use a feature's explicit public contract when cross-feature coordination is needed; selective `index.ts` exports may help, but do not add barrels to every directory merely to shorten imports.

| Category | Belongs here | Boundary |
| --- | --- | --- |
| `components/primitives` | Button, Card, Input, Select, Dialog, Badge, Tabs, Avatar, Spinner, Skeleton | Knows variants, sizes, states, accessibility, and visual tokens; does not know events, players, communities, or rankings. `JoinEventButton` belongs to its feature. Prefer the clear term `primitives` over `ui`. |
| `components/shared` | Potential PlayerAvatar, GameThumbnail, LocationChip, common branded EmptyState | Promote only when at least two independent features genuinely need the same Crowded Table visual concept. These are candidates, not required components. |
| `lib` | Supabase client/schema types, query-client configuration, generic validation, date/string utilities | Technical plumbing that can generally be described without product concepts. `joinChampionship`, `calculateEventAvailability`, and `getPlayerRanking` belong to their features. |

Keep a component in its feature until actual reuse justifies moving it. Neither `shared` nor `lib` should become a miscellaneous catch-all. Application providers compose infrastructure and feature providers; they should not absorb domain behavior.

## Community deactivation, archival, and settings

Use **Deactivate community account** and **Reactivate community account** for the participation relationship. Explain activity separately from standing: an inactive approved account can return without new approval; pending stays pending; suspended can reactivate but remains suspended; removed requires explicit reinstatement by effective active same-tenant staff with `can_approve_users`. Show a distinct Reinstate community account action to those authorized staff; it returns the existing account to approved/active and does not restore old bookings or staff access. Never present reactivation as clearing discipline, restoring bookings, or resuming staff permissions. Global app-account deactivation and permanent closure remain deferred.

Before deactivation, show a confirmation with the user's hosted/organized gatherings that have not started, including general title/time/type details and explicit notice that confirming will cancel them. Also list their personal upcoming bookings to withdraw and their guest bookings, explaining that guests remain registered unless explicitly removed before deactivation. If a guest booking belongs to a gathering being cancelled, explain that the row remains but the gathering will not occur. Offer a route to existing guest-management controls before confirmation; do not silently select guests for removal. Already-started gatherings are excluded. Cancel/dismiss makes no changes. Recheck the server's affected set before committing and refresh the confirmation when scope changes.

For active non-owner staff, explain that deactivation pauses their assignment and that active staff with `can_grant_staff` must manually restore their retained permissions later. Show paused separately from revoked; a community Reactivate action never resumes staff. Owners are explicitly exempt from staff pause: participation becomes inactive while ownership and management remain active. Require an active community account before initial non-owner staff assignment or resumption. Show **Resume staff access** only to effective active authorized staff for paused admin assignments whose community accounts are active; explain the unmet account-reactivation prerequisite otherwise; do not offer it for revoked assignments or imply permission-editing authority. Community reinstatement/Reactivate and staff Resume remain separate actions with separate permissions. Reconcile target activity and actor authority from server results; a race may invalidate a previously enabled action.

Inactive users retain their DM history, qualifying cancelled/archived gathering history, and their submitted reports. Hide/disable ordinary active gathering-chat participation and address access as directed by server authorization. Provide an authenticated **Archived communities** area with links into only the caller's existing DM and qualifying event/table history; preserve private audiences, resource-specific child access, and read-only state. Public community lookup remains unavailable, and history links never embed exact addresses.

Community Archive remains owner-only and requires an explicit consequence preview: every event/table that has not started will be cancelled, ordinary community participation will stop, and restoring the community will not reopen cancelled gatherings. Include private/official resources using safe details; preserve in-progress resources from automatic cancellation while explaining that the archived community still blocks ordinary writes. Refresh changed scope before confirmation and use server-confirmed results.

Expose `pause_community_events` to active staff with `can_manage_settings`, explaining that it prevents non-staff from creating community-public events/tables while preserving existing resources. Private creation is unaffected; active staff still require normal creation permissions. Settings flag editing, including auto-approval, requires this permission; settings access does not expose community archive/restore, staff-grant editing, tenant identity, or website-copy controls. Paused/revoked staff cannot use retained flags. Reconcile navigation, queries, and subscriptions after every activity/standing/staff/tenant-state change.

### Community removal and staff authority

Keep **Remove community account**, **Revoke staff access**, **Resume staff access**, and **Reappoint staff** distinct. Removal requires `can_remove_users`; standalone revocation requires `can_revoke_staff` and can revoke active or paused non-owner assignments. Revocation alone leaves community participation and gatherings intact. Removing an active/paused staff account also revokes the assignment and requires the acting staff member to hold both `can_remove_users` and `can_revoke_staff`. No assignment or already revoked status requires only `can_remove_users`. Explain a missing revocation permission before confirmation; recheck server authority and target status on submission, with no partial removal if requirements changed. Neither action may target the owner.

The removal confirmation lists the target's queued/confirmed personal bookings to withdraw and not-yet-started unofficial hosted/organized gatherings to cancel, with safe details within the actor's existing private-view scope. List relevant guest bookings separately, preserved by default, with explicit selection for cancellation under `can_remove_users`. Explain linked table-seat withdrawal for selected event registrations and preserve other people in mixed groups. Cancellation of a parent retains booking rows but makes the gathering unavailable.

Official gatherings are not listed or suggested for cancellation in this prompt. They remain collectively managed by staff with `can_manage_official_events`; any later cancellation uses their normal separate management flow. Personal upcoming reservations at an official gathering can still appear as bookings to withdraw. Exclude in-progress gatherings/reservations from automatic consequences and explain that ordinary live participation/chat/address access ends immediately. Cancel/dismiss performs no writes; refresh consent when the server's affected set changes.

Use `can_grant_staff` as the target permission name for creation/invitation and paused Resume, with a coordinated migration from implemented `can_create_admin`. A revoked assignment has no Resume action. Initially only the owner sees Reappoint staff, with fresh permission review and an active community account prerequisite. Community reinstatement does not restore staff or bookings. Record trusted non-owner reappointment as a future refinement, without enabling it through the renamed grant today.

## Table guest management

Accepted behavior, 2026-10-12: disabling `tables.allow_guests` prevents new guest bookings and preserves existing ones. Saving the flag does not remove people, release seats, or cancel event registrations. This is a planned table-management interaction; it is not implemented in the current prototype.

On disabling guests, show the authorized table manager which current bookings belong to guests, with an optional selection interface for removal. List each guest's optional name or stable unnamed-guest label, booking account, booking status, and group context where relevant. Start with no rows selected. Provide a clear keep-all/dismiss path and an explicit "Remove selected guest bookings" action; if no guest bookings exist, say so and offer no removal action. Explain that existing bookings stay unless deliberately removed. Selected removals affect this table only, including when it belongs to an event.

Saving the setting and removing selected bookings are separate mutations. Closing the prompt, selecting nothing, or a failed removal leaves existing bookings intact; report setting-save and removal outcomes separately so the user knows what succeeded. Refresh the authorized booking list and revalidate selected IDs when submitting removal. Use the standard cancellation command and reconcile capacity/group state from its result; do not optimistically remove unselected rows or infer removals from the flag's value.

Keep the same guest-removal controls available in the ordinary table-management interface at any time, whether guests are currently allowed or blocked. In this standard table-management UI, only users authorized to manage that table may edit the flag or remove bookings; private-view permission and unofficial-resource cancellation/archive moderation do not confer those actions. Per-person cancellation remains distinct from accepting only part of a group, which is prohibited. The [schema rules](03-database-schema.md#disabling-guests-and-removing-existing-bookings) and [backend patterns](06-backend-patterns.md#eventtable-rules--confirmed-2026-10-12) define the persistence behavior. The separate account-removal confirmation has the narrowly scoped can_remove_users guest-cancellation authority under D-108; it does not unlock this general table-management UI.

## Components and data flow

Prefer this data-access flow:

```text
UI component → feature query/mutation hook → feature API/data function
             → shared Supabase client → Supabase/PostgREST/RPC → PostgreSQL
```

The responsibilities are distinct: `getEvent()` describes how to retrieve data; `useEvent()` describes how React manages that server data over time; `EventDetails` presents it and coordinates user interaction. Keep table names, Supabase query construction, and cache lifecycle out of presentation components. Use strict TypeScript and explicit selected fields. Keep transactional operations in their existing authorized RPCs.

For example, an eventual `features/events/api/getEvent.ts` retrieves a safe event model, `features/events/hooks/useEvent.ts` wraps it in a query, and a component consumes `const { data: event, isLoading, error } = useEvent(eventId)`. This is an illustrative interface, not a finalized event table, query key, or API contract. Do not create two files for every trivial operation just to satisfy the diagram; retain the UI/data-access boundary where it makes the code clearer.

Preserve a useful distinction between presentation and data coordination: `EventCard({ event })` can render props while `UpcomingEvents()` may call `useEvents()` and handle loading/errors. A formal “container” naming scheme is unnecessary. Mock data and real data should be interchangeable behind these interfaces without redesigning visual components.

Keep render logic pure; use effects for synchronization, not derived state. React Compiler is the baseline; optimize measured issues rather than adding blanket memoization. See [React Compiler](https://react.dev/learn/react-compiler).

Share visual event/table cards and seat-state components only when useful; keep official admission and member-table authorization separate. A shared card must never accidentally display a private location or feed private table data into Community Home.

For attached tables, display the parent event's official/unofficial classification from the server projection, with no independently editable table selector (D-110). Standalone tables use their own classification. Drive management/moderation controls and removal previews from that same effective value and current permissions. Host identity and public/private audience remain separate. Any future attach/detach/move or sponsorship-change flow must use an authorized server command; changing a client field cannot change management scope.

## Server state, UI state, and types

TanStack Query is the planned server-state layer for events, profiles, game libraries, community information/posts, championships/standings, registrations, Meet & Play availability, and notifications. Let it handle caching, request deduplication, loading/errors, stale data, refetching, invalidation, and mutation lifecycle instead of repeatedly rebuilding these with `useEffect` plus `useState`.

An illustrative query identity is `['events', eventId]`; protected or tenant-dependent reads need the identity/tenant dimensions described below. Joining an event should invalidate the relevant event and affected lists so dependent UI reconciles with canonical server state. Optimistic updates may be useful for appropriate interactions, subject to the restrictions on seats, access, and results below.

Selected tabs, modal/drawer visibility, unsaved form text, and temporary display controls usually belong in local React state. Shareable filters belong in URL state. Introduce a lightweight global client-state library only if local state and existing providers cannot cleanly meet a concrete requirement. An Auth session/subscription lifecycle is distinct from ordinary cached resource queries; define that boundary during the refactor.

Prefer types such as `features/events/types.ts`, `features/championships/types.ts`, and `features/games/types.ts`, rather than a large global `src/types` collection. The infrastructure exception is generated `lib/supabase/database.types.ts`. A row with `event_type_id`, `starts_at`, and `max_players` might later map to an application model with `type`, `startsAt: Date`, `capacity`, and `spotsRemaining`. Introduce that mapping only when it helps; do not require one for every row today.

## Auth, access, and query state

Maintain explicit loading, visitor, pending/approved/suspended community-account, and resource-participation states. Paid membership and payment verification are deferred and must not appear as current eligibility types or gates. UI gating mirrors backend authorization.

Cache private data by user, tenant, resource, and filters. Example:

```ts
['member-tables', userId, tenantId, { category, from, cursor }]
['private-location', userId, tenantId, activityId]
```

Fetch private locations only after authorized confirmation, through their dedicated API. Do not load-and-hide them in general event data. Do not persist address or chat queries offline. Clear affected data/subscriptions on access change and discard stale responses from a previous identity or tenant.

TanStack Query is the intended server-state choice; form/validation libraries remain open. React Router in declarative BrowserRouter mode now owns URL navigation, nested application layout and not-found handling. The route map lives in `app/router.tsx`, with shared paths in `app/navigation.ts`; see D-121 and the implemented contract in the file-structure guide. Auth routes retain callback/recovery initialization and token cleanup. Old hash routing is removed.

Default light remains the only implemented theme. Reserve `styles/tokens/themes.css` for a later scheduled theme batch; do not create an empty theme file or alternate-theme fixture now. Future curated application/community themes must assign the full theme-dependent semantic/component contract at each scope, including nested default resets, without relying on inherited aliases to recompute. ## Introduce only when needed

Grow feature subdirectories, reusable components, schemas, query infrastructure, and mock interfaces when actual code needs them. Collections, messaging, notifications, and venues are possible future feature boundaries, not folders to scaffold today. Community DMs and event/table chat are now MVP; a messaging feature may own DMs when implemented, while gathering chat retains event/table authorization. Do not scaffold a generalized messaging framework before actual code needs it.

Do not automatically add `repositories`, `services`, `controllers`, `useCases`, `entities`, `domain`, or `infrastructure` layers to imitate backend/Clean Architecture patterns. Add an abstraction when it removes meaningful coupling, clarifies ownership, or makes change/testing substantially easier. Passing a simple Supabase call through several files is not sufficient justification. Selective barrels, row-to-UI mappers, global client state, and a configurable theme system need the same concrete justification.

## Forms and seat actions

Table creation captures title/game, schedule, category, experience, beginner flag, capacity, `manually_confirm_seats` (default false), `allow_guests` (default true), description, and public/private location. Keep private address input separate from public labels/descriptions.

Show requested/awaiting review, waiting for capacity, confirmed, rejected, and cancelled/withdrawn states. No current offer-acceptance button, offer countdown, reservation-expiry notice, checkout, or payment-pending screen exists. Confirmation is authoritative only after the backend commits.

In automatic mode, reservation requests and eligible queue promotion confirm the entire group immediately when capacity permits. Explain first-come, first-served among whole groups that fit; skipped groups retain their priority. Show a waiting state when confirmation is not yet possible, with withdrawal available. No later confirmation by the booking user is required.

In manual mode, authorized table managers review queued groups and choose Approve, Reject, or Notify about an issue. Approve confirms the group directly after server eligibility/capacity checks. Reject can include an optional reason; successful rejection removes the request from the active manager queue and promptly notifies the booking account with decision timestamp, rejecting user, and reason when present. Preserve decision details in history. An issue notice leaves the request pending and introduces no response deadline.

Before switching from manual to automatic confirmation, show a confirmation modal: "Queued requests will be processed automatically in the order received. Eligible groups will be confirmed when the whole group fits the available seats; groups that do not fit will keep their place in the queue." **Continue** submits the switch; **Cancel** closes the modal and leaves `manually_confirm_seats = true`. Opening or dismissing the modal must not save the toggle or process requests. While Continue is being submitted, prevent duplicate submission and do not present Cancel as an undo of a submitted command. After success, refresh the authoritative setting, queue, and confirmed bookings; on a lost response, reconcile server state before offering a retry. Show switch failures without claiming any confirmation succeeded.

Guest-name corrections and removals from a waiting group preserve queue position. Before an addition, clearly explain that the enlarged group receives a new queue timestamp; save the group change atomically and refresh its state. Approval actions reference the current request revision so stale manager screens cannot confirm the old group. If optional offers are introduced later, edits must revalidate those offers/capacity; that interface is deferred now.

Do not optimistically confirm a seat, match result, or address access. Preserve input on failure; reconcile server state after a lost response before retrying. Disable duplicate submissions for UX and rely on backend idempotency for correctness.

## Event cancellation and archive UI

Show Cancel Event/Table and Archive Event/Table buttons on the resource detail page only for authorized users and valid lifecycle states. For unofficial community-public resources, that is the organizer or staff with `can_manage_community_events`; private-view authority alone grants no controls. Official resources require staff with `can_manage_official_events` for creation and every management operation. Private organizers retain management of their own unofficial resources. No hard-delete or Reopen/Unarchive action ships.

A directly requested Archive action is enabled only while cancelled, with either zero registration/participation rows of any status at cancellation or at least 30 continuous cancelled days. Use server eligibility rather than counts from the currently filtered UI. Cancellation captures an optional reason and sends the accepted cancellation notices with timestamp and cancelling user. Follow the [accepted notification policy](06-backend-patterns.md#cancellation-notification-policy): one notice per affected user, guest/own-booking and child-table aggregation, organizer/host and pending-invitee notices, no unrelated staff broadcast, and no additional archive-only alert. Retain minimal notices and resolve details links against current historical access. Event cancellation/archival applies the corresponding stored status to attached tables through one backend command; no separate child buttons or client loops are required. Already-archived tables remain archived when the event is cancelled.

Cancelled community-public resources remain visible to anonymous visitors as well as signed-in users through a Cancelled filter and safe public details; private resources preserve their audience. Archived lists are no longer staff-only: eligible historical registrants/participants, guest bookers, former unofficial organizers, and authorized staff receive an Archived filter returning their permitted records. Historical rows of any state qualify; guest access belongs to the registering account, with no guest login. Private staff visibility still needs private-view authority or an independent organizer/history relationship. Invitations alone do not authorize private archives.

Display the resource's cancelled/archived state separately from preserved personal booking status. Explain that cancelling or archiving an event applies that status to its attached tables; show the server's resulting child states rather than merely inferring a display label. Already-archived children stay archived on parent cancellation. Submit a single event command for the cascade and do not mutate booking rows. Remove unavailable gatherings from upcoming activity/suggestions and disable booking/approval/promotion controls. Independently cancelling/archiving a table changes neither its parent nor siblings.

Immediately make affected chats read-only and clear participant-based exact-address access. Preserve the organizer's independently authorized location-management view where applicable; this grants no new staff or external-person access. Authorized historical viewers keep read-only chat access indefinitely after archival; do not hide it because their row was queued, rejected, withdrawn, or booked only guests. Active-table chat rules remain unchanged. Historic event access does not expose every child table/chat, and historic chat access never reveals a protected address.
