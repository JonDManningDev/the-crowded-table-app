# Secondary Auth checks: PostgreSQL 17 research

Research date: 2026-11-12. Documentation/source investigation only; this note neither changes the database nor establishes measured application costs. The parent investigation owns the current catalog inventory and local profiling results. Read together with [the A+B measurement record](auth-transaction-optimization.md), [accepted transaction decisions](../08-decisions-and-open-questions.md#ordered-actor-context-setup---implementation-authorized-2026-11-11), and [retained function dispositions](../23-api-policy-implementation-plan.md). Existing eligibility, trusted attribution, protected Auth access, retries and G-02 remain requirements.

## Evaluation counts and visibility

`STABLE` promises consistent results for identical arguments within a statement and permits optimizer reuse; it does **not** guarantee one execution per statement or transaction. SQL/PL functions marked stable read the calling query's snapshot. Volatile functions obtain a new snapshot for each SQL query they execute; marking identity/Auth lookups immutable would risk stale values in cached plans. These semantics mean repeated source references are neither measured calls nor proof of independent fresh eligibility checks. [PostgreSQL 17 function volatility](https://www.postgresql.org/docs/17/xfunc-volatility.html).

Boolean expressions can be reordered and unnecessary subexpressions skipped. Therefore count references as an inventory, then measure actual execution under representative predicates, row counts and denied/empty outcomes. Do not depend on expression order to set actor context before reading it. [Expression evaluation rules](https://www.postgresql.org/docs/17/sql-expressions.html#SYNTAX-EXPRESS-EVAL).

The PostgreSQL 17 scalar SQL inliner explicitly rejects `prosecdef` and non-null `proconfig`. Thus a SQL `SECURITY DEFINER` function with a function-local search path is not eligible for this scalar inlining route. The set-returning inliner has matching exclusions. This is a source-level fact, not an assumption based on the function's size. Preserve these security properties during profiling. [PostgreSQL 17 `clauses.c`, `inline_function` and `inline_set_returning_function`](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/backend/optimizer/util/clauses.c#L4353-L4360).

## Narrow profiling procedure

1. Record server version, isolation, function OIDs/definitions/owners/volatility/configuration, runtime identity, grants, relevant policies/defaults/triggers, dataset size and instrumentation settings. Preserve current source and catalog provenance. This follows the existing [A+B measurement practice](auth-transaction-optimization.md#reproducible-measurement-and-acceptance-plan).
2. Enable `track_functions = 'all'` only in the isolated measurement session using appropriate tooling privileges. `pl` excludes SQL functions; inlined SQL functions are omitted even with `all`. Do not interpret missing counters without checking configuration and inlining. Use the actual runtime role for measured application statements, without granting it instrumentation privileges permanently. [Runtime statistics settings](https://www.postgresql.org/docs/17/runtime-config-statistics.html#GUC-TRACK-FUNCTIONS).
3. In the **same connection and explicit transaction**, read a baseline from `pg_stat_xact_user_functions` immediately after `BEGIN`, then sample after setup and after each application statement, all **before COMMIT/ROLLBACK**. Subtract observations; do not treat an absolute value as this transaction's count. Despite the view's name and documentation shorthand, PostgreSQL 17 exposes backend pending function counters that can survive earlier commits until flushed (source details below). Cumulative shared counters additionally lag flushes and default reads cache values until transaction end; clearing the reader's statistics snapshot does not flush another backend. Use function OIDs, treat an absent row as zero only after proving tracking works, and retain calls plus total/self milliseconds. Total includes child functions, self excludes them; do not sum inclusive parent/child times. Instrumentation adds overhead. [Statistics visibility and function columns](https://www.postgresql.org/docs/17/monitoring-stats.html#MONITORING-STATS-VIEWS).
4. Run one small allowed, empty and denied sample per relevant operation, separating setup counts from secondary work. Include small and larger result sets to expose per-row amplification. For transactions that raise errors, record the error path and use a separate appropriately isolated cumulative observation if transaction-local reads are no longer possible. Then run ordinary latency measurements with diagnostic instrumentation disabled. This is a proposed investigation method, not a claim that a particular workload is currently slow.

Example observation query, issued separately from measured SQL:

```sql
select funcid, schemaname, funcname, calls, total_time, self_time
from pg_stat_xact_user_functions
where schemaname = 'app_private'
order by funcid;
```

### PostgreSQL 17 pending-counter correction

The local profiler observed absolute values growing across committed transactions (for example 50, 51, through 258, then 1). This is compatible with the implementation, not evidence of hundreds of calls in each request. `pg_stat_get_xact_function_calls()` returns `find_funcstat_entry(funcid)->numcalls`, and the corresponding time getters read the same entry. `find_funcstat_entry()` retrieves the backend's **pending** function entry; it does not select a transaction-specific counter. [SQL statistics accessors](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/backend/utils/adt/pgstatfuncs.c#L1532-L1557), [pending function lookup](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/backend/utils/activity/pgstat_function.c#L202-L217).

`pgstat_report_stat()` normally rate-limits flushing to one second, can defer for contention, and explicitly requires execution outside a transaction or transaction block. The ordinary backend loop likewise flushes only in its non-transaction idle branch; the idle-timeout handler applies the same restriction. Consequently, an explicit `BEGIN -> baseline -> measured work -> final sample -> COMMIT` keeps the ordinary flush boundary outside the delta interval, even if earlier pending calls exist. Do not collect the baseline before `BEGIN`, the final sample after `COMMIT`, or pool-hop between samples. Do not reset/drop function statistics during the interval; reject negative or missing-after-present samples as invalid. This source-based method supersedes any interpretation of raw `pg_stat_xact_user_functions` values as automatically reset per transaction. [Flush implementation](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/backend/utils/activity/pgstat.c#L532-L628), [backend idle handling](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/backend/tcop/postgres.c#L4332-L4385), [idle-timeout guard](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/backend/tcop/postgres.c#L3263-L3272).

`EXPLAIN (ANALYZE, BUFFERS, VERBOSE, TIMING OFF, FORMAT JSON)` can relate the outer query to rows, loops, filters and buffer work. `ANALYZE` executes the statement, including writes; any mutation probe needs an isolated fixture and rollback. `TIMING OFF` removes per-node clock readings while retaining total execution timing. Plan costs are arbitrary estimates, not milliseconds. An outer plan alone does not establish the execution count or inner Auth scan of an opaque definer call; pair it with counters or nested instrumentation. [EXPLAIN](https://www.postgresql.org/docs/17/sql-explain.html).

If already available, `pg_stat_statements.track = 'all'` includes nested statements; default `top` does not. Entries separate database, user, query ID and top-level status. Inspect nested rows under the definer owner too, rather than filtering only on the runtime role. Capture deltas without a global reset. Track planning only for a separate diagnostic question because it can add appreciable overhead. Nested and outer execution times overlap, so do not add them as disjoint request costs (measurement inference). [pg_stat_statements](https://www.postgresql.org/docs/17/pgstatstatements.html).

For a tiny dedicated diagnostic sample, `auto_explain.log_nested_statements = on` exposes statements inside functions; enable analyze/buffers and turn timing off if actual row counts suffice. Analyze instrumentation can affect all executed statements even when duration filtering prevents logging. Disable parameter-value logging with `auto_explain.log_parameter_max_length = 0`. This is an optional escalation of diagnostic detail, not necessary for the first count pass. [auto_explain](https://www.postgresql.org/docs/17/auto-explain.html).

## Integrity hazards for any later optimization

- **Lock lifetime and strength:** `FOR SHARE` conflicts with updates/deletes and normally persists until transaction end; `FOR KEY SHARE` does not protect non-key changes equivalently. Locks acquired after a savepoint can disappear when it is rolled back. Any cached eligibility proof must be invalidated when the lock/context lifetime ends. [Explicit locking](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS).
- **Post-wait snapshot:** under Read Committed, a locking select can follow a concurrently updated target and recheck its predicate, while other rows in the same statement still reflect the earlier snapshot. A completed lock statement followed by a fresh facts statement has different semantics from putting both into one joined statement. Repeatable Read/Serializable can require retry instead. Inference: a stable Auth read in an already-running outer statement is not automatically refreshed merely because another function acquired a row lock. [Transaction isolation](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED), [function snapshots](https://www.postgresql.org/docs/17/xfunc-volatility.html).
- **Time is separate from snapshots:** `now()`/`transaction_timestamp()` stay at transaction start. `statement_timestamp()` uses the latest client command's receipt time; it does not become the time after a lock wait. `clock_timestamp()` advances even inside a statement. Replacing the current ban-expiry comparison with either alternative changes behavior, including bans expiring during waits; preserve the accepted transaction-start contract. [Current date/time](https://www.postgresql.org/docs/17/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT), [existing expiry requirement](auth-transaction-optimization.md#lock-waits-and-snapshot-freshness).
- **Trusted context is a prerequisite:** a definer executes with its owner's privileges; removing it or widening Auth access to ease profiling changes the trust boundary. Keep secure search-path handling and narrow execution privileges. A cached UUID or eligibility flag is only evidence within the established trusted runtime/context contract; it is not independent token verification. Direct-call, anonymous, maintenance/provisioning, retry, pooled-connection and attribution paths must be classified before removing secondary checks. [Definer safety](https://www.postgresql.org/docs/17/sql-createfunction.html#SQL-CREATEFUNCTION-SECURITY), [repository dispositions](../23-api-policy-implementation-plan.md).

The narrow next decision is whether measured secondary calls materially contribute to real operation cost, and which callers already have a valid locked actor context. Counts, nested query time and end-to-end time answer different questions; none alone authorizes removing a retained guard.
