| D-061 | Eligible non-withdrawn groups are confirmed directly when their mode permits and they fit. Existing commercial prototypes are legacy refactor work, not target behavior. | Explicit user commercial deferral, 2026-10-12 |
| D-065 | Switching an existing table from manual to automatic confirmation requires a modal explaining automatic processing of queued requests in receipt order, subject to eligibility and whole-group capacity. Existing queue priority and first-fitting whole-group rules remain. | Explicit user mode-switch decision, 2026-10-12 |
| D-066 | No event hard deletion. All events can be cancelled; a cancelled event is eligible for archived status if it had no registrations at cancellation or has remained cancelled for at least 30 days. | D-068 | On event cancellation, notify users with any queued or confirmed registration, including cancellation timestamp, cancelling user, and optional reason. Guest-sponsor routing, extra recipients, and independent table-cancellation notices require the recommended mapping to be finalized. | Explicit user notification decision, 2026-10-12 |
| D-069 | Event/table cancellation must leave `event_registrations` and `table_participations` rows unchanged; do not mark a person's row cancelled because its resource was cancelled. Earlier group, queue, mode-switch, guest, and no-response-window decisions remain settled. Payments/memberships are deferred, not current blockers. Related community/table sponsor-attendance policies remain outside app functionality; no new `banned` column is implied.

Record accepted choices with date, rationale, affected files, and reconsideration triggers. Use separate ADRs only for substantial tradeoffs. Match each implemented workflow to its permission rules, state transitions, and acceptance examples.
