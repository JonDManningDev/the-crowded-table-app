## Accepted decisions

Published parent specification: [issue #5](https://github.com/JonDManningDev/the-crowded-table-app/issues/5). The user explicitly approved public publication; the issue is verified and labelled `ready-for-agent`. This is a planning artifact, not implementation authorization.

- Describe every public application table and its complete column shape in server database query types. Types describe structure, not permission to fetch or disclose records. PostgreSQL grants and retained RLS govern the runtime principal; API policies and HTTP projections govern callers. Replace the manually curated partial schema convention.
- Replace Supabase-generated server database types with one checked-in Kysely-native generated schema from the locally replayed database, using `kysely-codegen` as a server development dependency. Include application-owned tables in both `public` and `app_private`, independently of runtime grants; exclude Supabase-managed Auth tables and obtain protected Auth facts through narrowly privileged accessors. Match actual `pg` representations and read/insert/update/default/generated-field semantics. Preserve HTTP timestamp serialization and explicit cursor formatting. Apply the reviewed read-only nullable override for `tenant_staff_assignments.required_account_standing` and verify generated-column coverage from the catalog. The implementation plan records the investigated version/configuration; installation and generation remain unperformed.
- Make the API the default owner of product authorization and workflow orchestration. Review every retained database function, including functions invoked by triggers and RLS. Existing placement is not justification for retention. Retain database constraints, atomicity, trusted attribution, protected audit integrity and the accepted G-02 archive fence. Justify each retained function narrowly and inspect it for unnecessary business decisions. Review mixed functions for separation of privileged facts or integrity mechanisms from product decisions.
- Add feature-local `policies.ts` ownership: action-specific facts queries, decision functions, authorization requirements and SQL audience predicates. Services own transactions, coordination of locks and policy calls, mutations and workflow effects. Routes retain HTTP integration and operation invocation. Policies receive the operation's database/transaction handle. API-owned list authorization remains in SQL before pagination.
- Use named policy function exports with fact loading visibly separate from evaluation: for example, `loadEditConfigurationFacts(tx, actor, target)`, `canEditConfiguration(facts)` and `requireCanEditConfiguration(facts)`. Loaders perform reads; evaluators decide without database I/O; requirements throw the appropriate application error on denial. Add only functions with an actual consumer, without a mandatory class, factory or object wrapper. Colocate policy fact/decision types in `policies.ts`; operation input/result contracts stay in `types.ts`. Services coordinate these calls and reuse already-loaded facts within the operation.
- Services explicitly perform workflow effects; database safeguards reject invalid stored state rather than silently perform corrective workflows. In particular, deactivation explicitly clears `show_global_profile` in the same transaction. Retain a database safeguard and coordinating locks that reject inactive sharing, including concurrent attempts to enable it. Mechanical revisions and trusted timestamps may remain database-owned. The exact invariant implementation remains part of the function/trigger review.
- Keep reusable rules with their owning feature. `communities/policies.ts` exports narrowly named community audience/sharing facts or predicates; `user-accounts/policies.ts` composes them with global discoverability and bilateral-block rules. Ordinary community-profile access remains independent of personal blocks. Shared identity and transaction infrastructure retain their existing owners. Introduce neither a central policy registry nor a universal permission context; load the facts needed by each operation.
- The API owns semantic audit correctness and completeness: derive before/after from locked state, select the action and history categories, and commit the event with the mutation. Integration tests verify completeness, accurate details, category visibility and rollback. PostgreSQL protects event structure, trusted attribution, valid references and append-only rows/categories. This explicitly supersedes document 20's stronger requirement that PostgreSQL independently reject every protected transition missing its matching semantic event. A defective trusted writer could omit or misdescribe a semantic event; the database safeguards do not independently prove that event's semantic correspondence to the mutation.
- Shared transaction infrastructure retries confirmed SQLSTATE `40001` serialization failures and `40P01` deadlocks, with at most three total attempts. Retry the entire transaction, including actor context/eligibility, lock acquisition, fresh facts and authorization. Do not retry business denials, stale-input conflicts, arbitrary database errors or connection failures with uncertain commit outcome. Keep external side effects outside the retryable transaction. Preserve operation-specific replay/stale-request behavior; bounded transaction retries do not replace it.
- Retain `provision_user_account()` as a narrowly scoped Auth-platform integration: creation of an Auth identity atomically creates its required global application account. This is an explicit exception to API workflow ownership, not a fallback for community/account API workflows. Replacing it would require a new provisioning entry point and partial-failure/recovery contract.
- Retain `my_community_relationships()` as a fixed caller-only archive-safe projection, with reviewed fields/privileges and a community-owned adapter. It supports the user-account service's personal summary operation without exposing raw archived account/profile rows, preserving G-02.
- The first implementation scope ends with complete local verification. Follow the six dependency checkpoints in document 23, each with applicable verification, diff review and an independent commit once implementation is authorized. Hosted migration/verification is a separate subsequent step. Agreement with the design/scope does not start execution.

## Rationale and alternatives

The current `ApiTables` includes four tables, while the runtime privilege manifest covers additional public and private relations and services use raw SQL for omitted tables. A partial schema type is not an accurate privilege contract. Keeping schema descriptions separate from grants avoids maintaining an incomplete second permission inventory.

The persistent API transition already assigned operation-specific rules to the API, but some database functions, triggers and RLS policies still decide product audiences and permissions. Keeping those decisions merely because they were previously implemented in PostgreSQL would preserve the earlier architecture without evaluating its purpose. A private accessor for protected Auth facts or an archive-safe projection may still warrant database ownership; an entire workflow does not inherit that justification automatically.

Keeping all policy helpers inside `service.ts` would preserve the four-file convention but would not give authorization the explicit feature-local ownership requested in this review.

The existing Supabase generation describes timestamps as strings, whereas the server's default `pg` parsers return `Date` values for timestamp columns. Mapping every generated `Row` alone would retain that mismatch and omit distinct write semantics. Native Kysely generation avoids a separate adaptation layer with manually maintained timestamp overrides. Private application tables already have service consumers, so including them completes the application query model without widening database permissions.

### Audit enforcement finding and accepted resolution

Before this decision, document 20 required PostgreSQL to prevent protected transitions without matching semantic events and required before/after evidence derived from actual changes. The current community service pairs its mutations with `event()` inserts, while database attribution/detail-validation functions stamp context and validate payload shape. The read-only review found no independent constraint requiring every protected community-account/staff mutation to have a matching event, or comparing supplied before/after details to actual changed rows. Generic loggers for those tables were removed in migration `20261103000600`; archive/restore still has a database event trigger. No runtime bypass experiment was performed during this interview.

The user explicitly accepted API responsibility for semantic correctness/completeness after reviewing this gap and the tradeoff. The revised guarantee is deliberate, not a claim that independent database semantic completeness was previously verified. Move automatic semantic action/category selection into the API with matching tests; retain database structural, attribution, reference and immutability safeguards. Existing audit history is preserved.

Reconsider the boundary if a new trusted writer, external database surface, protected fact source or independently required integrity guarantee changes the justification. Reconsider type generation if it cannot accurately model the actual driver and write semantics. Add policy modules only to features with concrete authorization responsibilities.
