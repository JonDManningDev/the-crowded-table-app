# Hosted harness diagnosis

The initial hosted regression failed its first sharing/deactivation race with `competing operation must wait on the actual held root`. Teardown also reported a generic CLI query failure. Independent recovery found all 16 original application table checksums unchanged but three synthetic Auth identities remaining. Each was a UUID-address fixture created after the immutable baseline, whose synthetic Auth count was zero. Only those three recorded identities were deleted. `failure-recovery.json` proves original data and integrity restored.

The race failure reproduced with a measured 1,844ms observation deadline. A reduced real hosted HTTP reproduction captured a competing backend in a transaction-ID lock wait, blocked by the actual holder, at the deadline (2,007ms including the diagnostic query). A separate three-session advisory-lock probe confirmed restricted-runtime visibility through the session pooler. Thus neither missing lock visibility nor a missing service lock explained the failure: the HTTP competitor arrived at its lock late in a deadline that included the complete request setup. An authentication-only boundary still failed, demonstrating that the transaction/policy query lead-in also matters. The real verifier uses Supabase `getClaims`; it is neither replaced nor cached by the harness fix.

The harness now observes compilation of the exact competing root statement through a test-only Kysely plugin before starting the existing 1,800ms database-wait deadline. The first two races identify the account root, the block/source races identify the target account read/update, and the four archive/permission races identify the tenant root. The plugin returns each query and result unchanged. The test still requires `pg_blocking_pids` to identify the held backend before releasing the holder. It records request-setup and lock-observation durations for all eight races. A separate 6,000ms arrival bound releases the holder if the request fails to reach its root; the unchanged database idle timeout alone would not settle the JavaScript gate. Both requests settle before teardown, including failed-barrier paths. Local real Auth/PostgreSQL validation covers all four pairs in both orders, fresh retry denial, semantic audit/rollback/no-op/privacy and retained storage safeguards, with checksum-preserving cleanup.

The original CLI cleanup failure cannot be attributed retrospectively: the old wrapper discarded whether the child failed or its output failed JSON parsing. A no-write transaction probe returned valid JSON; subsequent cleanup attempts succeeded. The wrapper now distinguishes process failure (sanitized exit status/code) from response parsing failure without exposing SQL, credentials or child output. Teardown attempts every recorded Auth deletion even if the application-cleanup CLI reports failure, then requires independent all-table checksum, integrity and explicit Auth-ID absence proof. A failed command is not treated as proof of rollback or successful preservation.

No production verifier, service, route, migration, HTTP fixture, database grant or credential changed. The initial failures remain failures; later complete verification is recorded separately in `verification.json` and the execution checklist.
