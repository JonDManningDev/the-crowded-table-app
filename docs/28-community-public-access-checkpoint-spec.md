## Problem Statement

People should be able to discover a community through its Home content and the independently enabled minimal public directory without gaining access to its member sections. The current product mixes membership, public exploration settings and prototype paid-membership gates. Championship and own Profile do not follow the agreed audience distinctions, inactive people cannot consistently read their own saved community profile, and two stored settings describe public activity/chat exploration that is no longer intended.

The accepted simplification needs one coordinated checkpoint across client navigation, API contracts, database schema and authorization verification. Removing controls from the interface alone would leave obsolete contracts and inconsistent access behind.

## Solution

Preserve Community Home and its existing official-activity content. Require good standing for Meet & Play, Championship and Discussion, redirecting non-members to a shared joining/status destination. Permit the person's own Profile whenever they have a community account row, with inactive saved content read-only and standing-specific actions. Preserve the directory's separate visibility setting, minimal fields and effective staff badges.

Remove `allow_public_chat_visibility` and `allow_public_activity_visibility` throughout the stored schema, settings and landing contracts, callers and verification fixtures. Keep explicit joining, pending-request inspection/withdrawal and eligible return available outside restricted sections. Establish these behaviors using verified identity and current server state rather than the prototype membership toggle or a paid plan.

This issue implements the first checkpoint only. The accepted public About, global account History and real activity admission/chat features remain separately scheduled. Official activity visibility remains independent of admission: future implementation defaults official activities to community-public admission and requires deliberate selection of open admission for authenticated non-members.

## User Stories

1. As a signed-out visitor, I want to view Community Home without joining, so that I can discover the community.
2. As a non-member, I want Home's existing official-activity content and entry points preserved, so that the access simplification does not remove the community's introduction or official schedule.
3. As a non-member, I want visible official activities to remain visible even when I cannot participate, so that visibility and admission are understandable as separate concepts.
4. As a non-member opening Meet & Play directly, I want to reach the joining/status destination, so that I understand the membership requirement.
5. As a non-member opening Championship directly, I want the same membership boundary, so that an unguarded section does not expose restricted community content.
6. As a non-member opening Discussion directly, I want the same membership boundary, so that discussions are not a public browsing surface.
7. As an approved community member, I want to access those community sections, so that I can use the community I joined.
8. As a suspended community member, I want to retain good-standing section access while my existing action restrictions remain effective, so that page access does not silently change suspension policy.
9. As a signed-in person without a community account, I want an explicit joining action rather than automatic membership, so that community joining remains my choice.
10. As a signed-out visitor at a membership gate, I want a sign-in path, so that I can authenticate before taking account-specific actions.
11. As a pending applicant, I want to see my current application state, so that I do not submit a duplicate request or mistake pending approval for membership.
12. As a pending applicant, I want to inspect or withdraw my own request without entering member sections, so that I can manage my application.
13. As an eligible former member, I want the existing return workflow outside restricted sections, so that I can return without already needing member access.
14. As a person with a disciplinary restriction, I want the status destination to explain my applicable return restriction without offering a bypass, so that the interface reflects the server's decision.
15. As a user completing a join, withdrawal or return command, I want the displayed state to refresh, so that subsequent navigation reflects the actual outcome.
16. As a user whose displayed state became stale, I want the interface to reconcile the server response, so that an old button cannot grant an unavailable action.
17. As a user at the joining/status destination, I want community membership explained without a price or checkout flow, so that the gate reflects the current product rather than a paid-membership prototype.
18. As a user with any community account row, I want to reach my own community Profile, so that I can see the profile and status associated with that community.
19. As an inactive or removed community account holder, I want to read my saved community profile, so that I retain access to my own information.
20. As an inactive or removed account holder, I want that saved profile to be read-only, so that its visibility does not restore editing privileges.
21. As an inactive account holder, I want status and applicable return controls alongside my profile, so that I understand how to proceed.
22. As a pending account holder, I want my existing onboarding/profile-editing rights preserved, so that this simplification does not prevent onboarding.
23. As an approved or suspended account holder, I want my existing profile-editing rights preserved, so that section gating does not silently change my profile permissions.
24. As a person without a community account row, I want own Profile to lead to joining/status rather than a fabricated profile, so that the page reflects an actual relationship.
25. As a community account holder, I want my new self-read right to grant no access to another person's profile, so that private profile audiences remain intact.
26. As an archived community's non-owner, I want the archive restriction to remain effective even for my own community profile, so that ordinary self access does not override the accepted archive fence.
27. As an archived community's owner, I want my existing authorized management access preserved, so that this change does not remove owner lifecycle capabilities.
28. As a visitor to a community with its public directory enabled, I want only eligible display names and effective role badges, so that I can recognize the community without gaining profile or communication access.
29. As a community settings manager, I want to retain the independent public-directory setting, so that directory exposure remains a separate choice.
30. As a visitor to a community with its directory disabled, I want no directory grant from Home access, so that public introduction does not imply public membership enumeration.
31. As a suspended community account holder, I want directory eligibility preserved without an ineffective staff badge, so that membership visibility and current staff authority remain separate.
32. As a community user, I want paused and revoked assignments to produce no staff badge, so that public presentation does not imply authority that is no longer effective.
33. As a directory reader, I want no profile click-through, DM grant or account identifiers added by this change, so that a minimal directory stays minimal.
34. As a settings manager, I want the obsolete chat/activity visibility controls removed from the current contract, so that I cannot configure behavior the product no longer supports.
35. As a community owner, I want auto-approval, creation pause and directory visibility preserved with their existing management authority, so that unrelated settings remain stable.
36. As a client developer, I want removed settings rejected on writes and absent from responses, so that stale callers cannot silently depend on retired behavior.
37. As an operator, I want populated community data and audit history preserved during the schema change, so that dropping obsolete settings does not damage unrelated records.
38. As a user switching accounts or revisiting a direct URL, I want access evaluated for my current identity and relationship, so that another session's state cannot expose restricted content.
39. As a keyboard or mobile user, I want the changed gate and Profile flows usable at relevant screen widths, so that the simplification works across supported navigation modes.
40. As a user with independently authorized personal history, I want ordinary section gates kept separate from resource authorization, so that this checkpoint does not preclude the agreed DM/report history and later activity-history links.
41. As a maintainer, I want preview fixtures clearly distinguished from persistent authorization, so that a working mock is not reported as a completed live join flow.
42. As a maintainer, I want the first checkpoint independently verified and documented, so that deferred About, History and activity features are not accidentally bundled into its completion claim.

## Implementation Decisions

- **Scope:** implement the agreed first checkpoint across the client community-navigation/join-status/Profile modules and the server community landing/settings/profile operations, their contracts, database query types, migration dependencies and fixtures. Add no About, History or real activity admission/chat feature in this issue.
- **Vocabulary:** good standing means approved or suspended community standing. Having a community account is a separate fact. Community-public means the good-standing community audience. Open means admission permits authenticated non-members, independently of official sponsorship or anonymous visibility. Preserve separate action, resource and lifecycle authorization.
- **Existing state:** both retired flags already exist in local schema migrations and server settings/landing responses. Neither is currently a client visibility control or a real activity/chat implementation. Existing community routes use a mock membership toggle; only Meet & Play and Discussion currently have guest gates. Preserve this distinction when reporting verification.
- **One section-access owner:** centralize the client decision for good-standing sections versus any-account own Profile. Redirect non-members from Meet & Play, Championship and Discussion to one shared joining/status destination, including direct navigation. Restrict own Profile when no community account exists. Keep independently authorized resource/history URLs outside this blanket section gate.
- **Verified state:** use authenticated server results for live account presence, standing, request and restriction state. Reuse the existing exact-slug landing, exact verified-self account facts, own activation-request and controlled command operations where their contracts suffice. A missing own-account result may represent no community account only after community availability and authentication are established; transport/auth failures must not be converted into an available Join action. Derive self from verified identity and validate stored tenant relationships.
- **Preview/live wiring:** establish community identity and route/context wiring needed by the existing client gates before dependent joining actions. Explicit fixture states may exercise preview presentation but cannot establish live authorization or real join completion. Keep this work limited to the gate, own Profile and required adapters rather than a broad community-feature or activity-feed cutover. If a required exact-self fact cannot be supplied by existing operations, define the narrow actor/rows/fields/enumeration contract before adding it; do not widen directory or other-profile reads.
- **Joining/status:** preserve sign-in, explicit joining, current application inspection/withdrawal and eligible return, including restricted-state explanations. Use existing serialized command semantics and server eligibility. Refresh relationship/request state after commands and stale responses; prevent accidental repeated submissions through the existing pending-action conventions. Do not introduce new authentication return-routing policy. Remove the affected paid-membership gate, price and checkout action; preserve unrelated Home promotions and prototype activity behavior outside that gate.
- **Own Profile:** change the server result audience so verified self with any community account row in an active community can read their saved profile. Inactive/removed self access is read-only. Preserve current pending/approved/suspended edit rules, exact response field contracts, non-self bilateral block rules, other-profile audiences and owner-only archived account-content access. Do not turn inactive profile-management capability on or permit inactive profile/preference writes.
- **Public directory:** retain its independent setting, existing endpoint, opaque pagination and target filtering. Return only eligible approved/suspended targets' community display name and effective staff role badge. A badge requires approved standing plus an active assignment; paused/revoked roles produce no badge. No account ID, standing, dates, biography, audit metadata, full-profile or DM authority is added. Keep existing absent-profile handling. Directory placement is deferred.
- **Retired settings:** remove `allow_public_chat_visibility` and `allow_public_activity_visibility` from settings inputs/outputs, field constants, public landing types/schema/projection and all typed callers. Strict input validation must reject either retired key rather than ignoring it. Retain `auto_approve_users`, `pause_community_events` and `allow_public_directory_visibility`, their defaults and current management authority.
- **Migration:** use a new forward migration that drops the two obsolete columns and reconciles dependencies explicitly. Preserve historical migrations and retained application/audit data. Avoid indiscriminate dependency cascading. Regenerate the complete database query types from a clean local replay and reconcile runtime/schema manifests and fixtures. Add no replacement visibility flag, compatibility alias or parallel legacy interface.
- **Architecture:** preserve the existing feature service/policy/HTTP ownership model. Services own returned-value SQL and inline audience conditions; policies retain fact gathering and decisions; routes and transport schemas retain HTTP ownership. Preserve the trusted least-privileged API role, G-02 archive RLS, protected Auth access, mutation scope, trusted attribution, storage integrity and append-only audit safeguards. Do not reintroduce product-audience RLS or external application Data API grants.
- **Intentional contract change:** update the reviewed HTTP contract only for the deliberately removed fields and associated strict writable shapes. Preserve unrelated paths, projections, statuses and operation ownership. Do not regenerate the baseline merely to hide a failure.
- **Deferred activity contract:** retain official Home visibility. Later real official activities default to community-public admission and require deliberate open selection; open participation creates no community account and grants only participant-scoped activity chat under applicable admission/lifecycle rules. These rules guide future features, not new activity columns or functionality in this issue.
- **Documentation and closeout:** reconcile intended requirements, current implementation status and deployment status separately. Preserve historical milestone evidence. Review the scoped diff, respect existing unrelated edits, and commit the authorized implementation checkpoint independently after its required gates pass. Hosted deployment is not part of specification publication or this local implementation checkpoint.

## Testing Decisions

- **User-confirmed boundaries:** use existing real Supabase Auth through HTTP API to PostgreSQL integration tests as the primary authorization/contract boundary. Use existing observable React navigation/control tests plus browser checks for client behavior. Retain existing database migration, runtime-role and external Data API safeguard checks. Add no internal policy/service mocking seams.
- **Good tests:** assert externally observable results, allowed fields, rejected writes, denial behavior, navigation and persisted outcomes. Avoid tests that mirror function decomposition or assert which internal helper/query builder ran. Injection-only tests establish HTTP wiring and serialization, not database authorization correctness.
- **Prior art:** extend the existing real Auth/HTTP configuration, directory and self-service integration suites and their local HTTP harness; reuse the existing community lifecycle/request and retry/concurrency fixtures. Retain the HTTP-contract baseline and runtime/external access-audit conventions. For the client, extend existing React Testing Library/Vitest route, guest-gate and Profile tests, supported by responsive browser checks. Do not introduce a second testing framework or a new service-mocking layer.
- **Client audience matrix:** cover signed out, authenticated without an account, pending, approved, suspended, inactive, disciplinary-restricted inactive, archived owner and archived non-owner. Verify Home preservation; good-standing section access; any-account own Profile with read/edit/archive distinctions; and applicable sign-in/join/request/return/status controls. A stored inactive standing plus a restriction flag represents disciplinary removal; do not invent a new removed enum state.
- **Navigation/state:** verify direct URLs, back/forward, refresh, account switching, loading and refreshed standing/request changes. Do not render restricted content while eligibility is unresolved. Apply the existing refresh/navigation revocation policy; no new push invalidation requirement. Confirm a History/referrer parameter, preview toggle or directory row cannot grant access.
- **Own Profile real allow/denial pairs:** inactive self read versus inactive-other read denial; own read versus inactive write denial; existing pending/approved/suspended edits versus their nearest denial; active-community self read versus archived non-owner denial and retained owner management. Preserve non-self block behavior and exact field projection. Test forged actor/tenant/target inputs and removed client filters.
- **Settings and landing:** prove both retired keys are absent from settings/landing responses and rejected in strict writes, including mixed patches. Retained settings, defaults and management audiences remain correct. Cover exact-slug lookup and identical unknown/archived public unavailability. Existing seven hero/welcome overrides retain only their accepted public text projection independently of the directory flag.
- **Directory regression:** verify on/off behavior, every page's current authorization, approved/suspended target filtering, missing-profile handling, effective approved-active badges, paused/revoked/suspended badge absence, opaque cursor validation and the exact minimal row fields. Probe expanded columns, raw identifiers and related-resource access through surfaces that actually exist.
- **Joining and stale transitions:** exercise real explicit joining, pending-request inspection/withdrawal and eligible versus restricted return through current HTTP operations. Verify stale request IDs/revisions, retry outcomes and concurrent lifecycle/approval/withdrawal cases relevant to changed flows. A UI command success must be backed by persisted state; preview simulation does not satisfy this test.
- **Database/external safeguards:** run clean migration replay and populated forward upgrade; compare retained application/audit records and inspect retained integrity/runtime manifests. Verify only the intended columns/dependencies are removed, generated types match replay, retained G-02/mutation/attribution protections hold, and anonymous/authenticated external Data API callers gain no application-table access. Test direct-runtime bypasses under the actual runtime role; retain joins/embedding checks where applicable.
- **Required checks:** run the applicable real integration, authorization, concurrency/retry, database safeguard, HTTP-contract, client, TypeScript, lint and build gates from the accepted architecture plans. A required failed or unavailable gate blocks implementation completion until resolved or explicitly adjudicated. Review intentional contract changes rather than clearing them through blanket baseline regeneration.
- **Visual/accessibility verification:** check Home preservation and changed gate/Profile states at relevant mobile, tablet and desktop widths, including pending, inactive and disciplinary states. Check keyboard navigation, focus and actionable/read-only controls without redesigning unrelated components or shared tokens.
- **Honest verification scope:** About editing, the History feature and real official open admission/chat require their own later allow/denial, lifecycle, stale-input and concurrency checks. Do not claim this issue implemented or verified those features merely because their future contracts are documented.

## Out of Scope

- Building, styling or choosing storage/editor structure for the public About page. Its accepted future content authority remains eligible `can_modify_content` staff.
- Implementing the global account History destination, its exact fields or lifecycle-based resource entitlements. Preserve the accepted direction of actual activity links with independent authorization.
- Implementing real official activity admission, activity fields/editors/admission transitions, participant chat, booking or guest workflows. Preserve existing Home content and separate these future capabilities from section gating.
- Opening unofficial community-origin activities to authenticated non-members; this remains a future expansion.
- Adding generic public unofficial activity, Discussion or chat browsing, or replacement public visibility flags.
- Changing the public directory's placement, adding identifiers/profile click-through, widening its projection, or granting messaging rights.
- Changing disciplinary policy, suspension's operation-specific rights, global account deactivation, blocks, private addresses, archive/history policy or staff authority beyond the expressly accepted inactive self-profile read.
- Building a complete community feature cutover, replacing mocked feeds, introducing payments, or changing unrelated prototype Home promotions/activity checkout simulations.
- Changing authentication return-routing policy, shared design tokens, styling dependencies or the completed persistent API architecture.
- Compatibility fallbacks, legacy aliases, production rollout/recovery planning, hosted migration execution, application hosting or deployment.
