# Database schema plan

Status: initial auth/account/tenant migrations are implemented in `supabase/migrations/`; broader domains remain unimplemented. Accepted event/table decisions below are distinguished from remaining relational proposals. See [database implementation and validation](../supabase/README.md) for executable contracts and local setup. Deployment to a hosted database remains a separate step. The 2026-10-14 deactivation, staff lifecycle/permission changes, disciplinary removal, settings permissions, and archival-cancellation decisions are target changes requiring additive migrations and command/UI updates; they are not implemented by these documentation edits.

The 2026-10-15 profile direction adds global `user_account_profiles` alongside curated `community_account_profiles`, with atomic community joining and profile submission (D-111/D-112). D-113–D-115 settle separate community profile visibility, global search/matchmaking controls, and account-level blocking with private labels instead of a public ID. Q-016 retains only follow-up audience, lifecycle, and UX details. These are architecture plans, not implemented schema or UI changes.

Current planning scope (2026-10-12): payments and paid memberships are deferred until one of the last implementation stages. Until then, app behavior has no fees, checkout, manual payment verification, paid entitlements, or membership gates. Community accounts, standing, tenant permissions, privacy, and resource registration remain required. Historical commercial tables/rules below are future-only; legacy prototype payment/member simulations are not the target behavior.

## Conventions and tenant boundary

Propose community = tenant. Community-owned business tables carry `tenant_id`; global account identity, global user profiles, and main-account personal blocks are explicit exceptions. Community-agnostic matchmaking and event hosting are planned product directions whose resource/access models remain to be designed; do not apply existing tenant-only rules to them by assumption. Use UUID IDs, database-managed timestamps, `timestamptz` instants, and an IANA community timezone (proposed launch value `America/Tegucigalpa`). Use HNL minor units for monetary values, with currency stored explicitly. Prices are configurable.

All cross-entity references within a tenant use composite foreign keys to matching unique keys, such as `(tenant_id, event_id)` or `(tenant_id, table_id)`. RLS controls access; these constraints prevent structurally invalid cross-tenant references.

### Canonical naming and audit conventions

- Table names are always plural and `snake_case`. Column names are always `snake_case`.
- A child table uses a singular prefix based on its parent entity: `tenants` → `tenant_staff_assignments`, `tenant_website_content_overrides`; `tables` → `table_locations` → `table_location_details`. Apply this consistently when finalizing the physical schema; older conceptual table labels below and elsewhere in the planning docs must be reconciled before migrations, not treated as naming exceptions.
- Every table includes `created_at`, `updated_at`, `created_by`, and `updated_by` by default, including join tables. These standard fields are implicit in the table summaries below rather than repeated in every row. Any omission requires a documented table-specific reason; for example, a genuinely immutable, append-only table may omit update fields because updates are prohibited.
- `created_by` and `updated_by` are nullable UUID foreign keys to global user accounts, not community accounts: staff may act without being participants. SQL `NULL` means the system acted, not unknown attribution; no system account or UUID is needed. Trusted database/backend code sets timestamps and actor attribution; clients cannot choose or rewrite audit actors. Human-initiated actions retain the initiating user's attribution even when performed by backend code or workers. Creation initializes both actor fields to the creator (or both to `NULL` for system creation); updates preserve `created_by` and set `updated_by` to the acting user or explicitly to `NULL` for system updates. Signup provisioning normally attributes creation to the newly registered user, establishing that reference safely.
- Persist additional audit detail when needed through specific additional audit columns. Standard actor columns record creation and the latest update, not full history; sensitive commands still require `tenant_admin_actions` records.
- Initially prohibit hard deletion of referenced user accounts, including references from staff assignments, community accounts, and audit actor columns. Use restrictive foreign-key deletion behavior; do not cascade-delete dependent business records or use `ON DELETE SET NULL` to erase human attribution, since `NULL` means system. Auth identity deletion must not indirectly bypass this restriction through cascading account deletion. The eventual anonymization/auth-deletion workflow remains deferred and requires an explicit design preserving attribution and tenant ownership before it is enabled.

## Tenant identity, website copy, and settings

Keep `tenants` focused on the community's identity, primary geographic base, and lifecycle:

| Column | Requirement / purpose |
| --- | --- |
| `id` | UUID primary key |
| `slug` | Required lowercase, unique community URL identifier; reserved names prohibited; immutable after creation initially |
| `name` | Required community display name |
| `country_code` | Required standardized two-letter country code, such as `HN` |
| `state_province` | Nullable region name; plain text initially |
| `city` | Nullable city name; plain text initially |
| `timezone` | Required IANA timezone; do not infer solely from country |
| `operational_status` | Not null; `active` or `archived`, default `active`; transitions through controlled owner commands |
| `created_at`, `updated_at`, `created_by`, `updated_by` | Standard audit fields defined above |

Normalize blank optional location input to `NULL`. One primary geographic base does not need a separate tenant location table. Event venues and private addresses remain separate. Defer geographic reference tables, coordinates, street addresses, and postal codes until needed. Ownership remains authoritative in `tenant_staff_assignments`; do not duplicate it with `owner_user_id` on `tenants` or infer current ownership from `created_by`.

Tenant lifecycle initially supports `active` → `archived` and `archived` → `active`. Archiving prevents ordinary community participation and ordinary tenant-scoped writes while preserving owner access for explicit management/restoration operations and authorized read-only history under D-100. Confirmed community archival cancels events/tables that have not started, preserving per-person rows and using existing cancellation notices (D-101). Archive is reversible and does not delete data, revoke the owner assignment, or remove the exactly-one-active-owner requirement. Restoration does not approve accounts, reactivate community accounts, resume paused staff, reinstate suspended/removed participants, or reopen events/tables cancelled during archival. Initially only the owner may archive or restore the tenant; platform suspension is deferred. Enforce tenant state in backend authorization, not merely navigation or hidden buttons.

Tenant slugs are 3–63 lowercase ASCII letters/digits with single separating hyphens, unique, and exclude the route names enumerated in the first migration. Enforce these rules in the backend/database, including uniqueness under concurrent creation. Slugs cannot be changed after creation in the initial version, even by the owner. Maintain the reserved-name list alongside routing changes. The slug identifies a community but never grants authority.

### Public tenant representation

For this milestone, provide a dedicated public lookup by slug for active tenants. Return only `id`, `slug`, `name`, `country_code`, `state_province`, `city`, and `timezone`. These location fields describe the public geographic base, never a private meeting address. The identifier grants no authority. Do not return `operational_status`, timestamps, audit actors, staff assignments/owner identity, permission flags, tenant settings, community accounts, or profiles through this interface. Website copy retains its separate page-specific visibility rules.

Enforce the explicit field list and active-tenant filter in the backend/database; the browser must not receive full rows and hide fields. Direct queries, joins, or alternate interfaces must not bypass the boundary. New tenant columns stay private until explicitly approved for public exposure. Archived tenants are absent from public slug lookup; show a generic “Community unavailable” result without exposing archive status, while preserving authenticated owner management/restoration access. A separate authenticated Archived communities history entry point exposes only the caller's authorized DM and qualifying event/table history; this does not expand public lookup.

A “Find Your Next Community” discovery page and general community listings/search are deferred to a later release. This milestone supports individual community lookup by slug, not a browsable directory.

### Website copy overrides

Add `tenant_website_content_overrides` (the plural table name for the previously discussed website-content concept). The application owns page structure, supported sections, behavior, typography, and illustrations. Tenants customize only predefined text slots.

| Column | Requirement / purpose |
| --- | --- |
| `tenant_id` | FK to `tenants`; part of composite primary key |
| `content_key` | Application-defined slot identifier; part of composite primary key |
| `text_value` | Required replacement text |
| `created_at`, `updated_at`, `created_by`, `updated_by` | Standard audit fields; editors reference global user accounts |

Example slots for the Community page (keys are data values, not column names):

| `content_key` | Example copy |
| --- | --- |
| `community.hero.eyebrow` | People make the best games |
| `community.hero.heading` | A place to belong. |
| `community.hero.description` | Same table. More friends. Make yourself at home. |
| `community.welcome.eyebrow` | Your little corner of Tegucigalpa |
| `community.welcome.heading` | Come for a game. Stay for the people. |
| `community.welcome.body` | Ask a question. Share a favorite. Say hello to someone new. |
| `community.welcome.emphasis` | There's a whole community around you. |

Enforce uniqueness on `(tenant_id, content_key)`. Accept only application-defined keys, with slot-specific length limits and plain text/supported line breaks; do not accept arbitrary HTML, scripts, layouts, or behavior. A missing override uses the application default; resetting to default deletes the override. Location-aware defaults derive from the tenant location and have a fallback when city is absent. Saved custom copy remains explicit text and is not automatically rewritten when location changes. Action labels such as “Start a conversation” remain application-controlled initially.

Content reads follow the intended page's visibility: private Community copy is not automatically public. Public projections expose display text without unnecessary audit actor IDs. Owners may edit copy without a community account; any later explicitly authorized non-owner admin must satisfy the active-community-account staff invariant; enforce authorization and actor attribution at the backend. See [customization permissions](04-auth-and-multi-tenancy.md#community-customization-permissions).

### Settings and boundaries

Add `tenant_settings` as a one-to-one operational configuration table. Use explicit typed columns rather than an unrestricted key/value or JSON configuration store for operational or authorization rules. Its target fields, including the accepted follow-up pause flag, are:

| Column | Requirement / purpose |
| --- | --- |
| `tenant_id` | Primary key and FK to `tenants` |
| `auto_approve_users` | Boolean, not null, default `false`; controls initial approval of new community accounts |
| `pause_community_events` | Boolean, not null, default `false`; when true, non-staff cannot create community-public events or tables. Active staff retain the exception subject to all existing creation permissions. Existing resources are preserved; private creation is unaffected by this flag |
| `created_at`, `updated_at`, `created_by`, `updated_by` | Standard audit fields |

Create the settings row in the same transaction as the tenant and owner assignment. New community accounts start as `pending` when `auto_approve_users = false` and `approved` when it is true. The creator's optional community account is automatically approved during tenant creation regardless of this setting. Approval does not grant paid membership benefits. Changing the setting affects future joins only; it does not approve existing pending accounts or reinstate suspended/removed accounts. The implemented milestone restricted settings edits to the owner; D-102 changes the target rule to active same-tenant staff with `can_manage_settings`. Permission to approve individual users still grants no settings authority. `auto_approve_users` governs new community accounts, not self-reactivation of an existing non-removed account.

Add `can_approve_users` to `tenant_staff_assignments`: boolean, not null, default false for non-owners and always true for owners. Effective active same-tenant staff with this flag may approve pending community accounts and explicitly reinstate removed community accounts (D-104). The reinstatement command atomically changes removed/inactive to approved/active on the retained account, preserving identity and disciplinary audit history. It does not restore cancelled gatherings, withdrawn bookings, or paused/revoked staff assignments. This permission grants no suspension/removal, suspension-lifting, staff assignment/resumption, permission editing, settings, or entitlement management. The owner controls grants of the flag. The implemented milestone's pending-only approval command must be deliberately extended or complemented by a distinct reinstatement command.

`can_grant_staff` is the target name for the existing `can_create_admin` permission (D-106), not a second independent grant: boolean not null, default false for non-owners and always true for owners. Effective active same-tenant staff with this flag may create admin assignments, issue future admin invitations, and explicitly resume paused admins with retained permissions (D-099). New assignments still start with all-false permissions. The flag does not authorize editing permission values, revoking staff, reappointing revoked staff, changing ownership, or removing community accounts. Invitation redemption must validate trusted recipient, tenant, expiry, one-use status, and issuing authority atomically; recipients cannot supply roles or grants. Invitation delivery/UI remains to design.

For the initial implementation, every administrative permission defaults to `false` for non-owner staff, not only `can_approve_users`. The admin role alone grants no administrative capability; each action requires its explicit permission. Future permission flags follow the same default. A later community-staff configuration UI will allow the owner to choose tenant-specific default permissions for new admins and customize individual admins' permissions. These configurable defaults and their persistence model are deferred; do not add speculative columns or tables for them in the first migrations. Defaults for new admins must not silently rewrite existing admins' individual grants.

All administrative permission flags, including `can_approve_users`, `can_grant_staff`, `can_remove_users`, `can_revoke_staff`, and any future flags on staff assignments or related permission tables, must initialize to and remain `true` for the owner. Owner creation sets all such permissions to true atomically; the future ownership-transfer command must do the same. Enforce this invariant in the database as well as authorization code: reject false/null owner permissions and prevent deletion of required owner permission records. New permission migrations must initialize existing owners to true and extend enforcement; admin defaults remain false. A blanket `DEFAULT false` alone does not implement role-dependent owner defaults. Other detailed administrative permissions remain to be defined.

Add `tenant_staff_assignments.can_remove_users` and `can_revoke_staff`, both non-null booleans, default false for non-owners and always true for owners (D-106). Effective active same-tenant staff with `can_remove_users` may remove a non-owner community account and explicitly select that account's guest bookings for cancellation within the removal flow. This is not unrestricted booking-edit authority. `can_revoke_staff` authorizes changing a non-owner staff assignment from active or paused to revoked; it does not change community standing/activity or cancel bookings/gatherings by itself. Neither flag grants permission editing, staff creation/resumption/reappointment, private-data reads, or suspension authority. Owner protections apply to both commands. Removing a community account with an active or paused staff assignment requires both permissions on the acting staff member; no assignment or an already revoked assignment requires only `can_remove_users`, subject to all other authorization checks.

### Global and community profiles — accepted target 2026-10-15

The implemented first milestone has `user_accounts`, `community_accounts`, and `community_account_profiles`, with community-account creation allowed before profile setup. D-111/D-112 extend that baseline rather than rename or replace the community table. Auth remains authoritative for credentials and login identity details. Global account records remain distinct from personal presentation.

Add `user_account_profiles` with `user_id` as its primary/foreign key to `user_accounts(user_id)`. Retain `community_account_profiles` with primary/foreign key `(tenant_id, user_id)` to `community_accounts`. Both profile types initially contain a required trimmed nonblank `display_name` of 1–80 characters, nullable `bio` of at most 2,000 characters, and standard audit fields. A user can maintain their global profile without joining any community. Each community profile is independently curated for that community's focus and culture. Defer photos, profile location, experience, play style, teaching flags, and interests until implemented; the scope/taxonomy of future matching interests is a separate decision.

The community join form pre-fills both fields from the caller's existing global profile, allows edits, and submits the resulting community profile with the join request. The backend creates the new community account and its profile in one transaction, deriving identity from the verified caller and standing from existing community policy. Store the submitted values as an independent copy: later edits in either profile do not automatically change the other, and a deliberately empty community bio must not fall back to the global bio. Missing global data leaves fields for the user to complete; it does not require creating a global profile through joining. Global-profile onboarding timing remains open.

Apply the same profile-submission behavior when a community creator opts into participation: owner/settings/tenant creation, approved community participation, and the submitted community profile commit together. Opting out creates no community account or community profile and does not affect an existing global profile. Profile completeness remains separate from staff authority. Existing accounts without profiles need a rollout/setup path; do not fabricate display names or silently select one community profile to populate a global profile. Retries and existing-account reactivation/reinstatement must preserve standing, identity, and prior profile edits; joining is not an implicit profile overwrite or discipline reset.

Profile ownership does not determine its audience. Global-profile self-management is independent of tenant activity or community standing; community-profile edits remain subject to the applicable community lifecycle rules. Community directories display the community profile, not an automatic global fallback. D-113/D-114 establish three independent self-controlled flags:

| Flag | Stored on | Default | Meaning |
| --- | --- | --- | --- |
| `show_global_profile` | `community_accounts` | false | Permit other users in this community to see the global profile through its authorized community audience |
| `user_is_discoverable` | `user_accounts` | true | Allow other users to find this account in standard global account searches |
| `enable_matchmaking` | `user_accounts` | true | Enable participation in global, non-community matchmaking, independently of standard account search |

Do not require `user_is_discoverable` for community-authorized global-profile reads or for global matchmaking. A user can be visible through a community while absent from global search, or be eligible for global matchmaking while absent from search. Conversely, searchability does not enable matchmaking or set any community's `show_global_profile`. Matchmaking preferences do not govern community matchmaking. These flags are eligibility/audience controls, not permissions to message, invite, enumerate affiliations/history, or bypass account restrictions and blocks. Missing profile data still needs normal feature handling; a true flag does not fabricate a profile or automatically create a match.

Eligible community viewers, multiple-shared-community composition, read revocation, and search/matchmaking response fields remain follow-up policy details under Q-016; the flag names, locations, defaults, and independent purposes are settled. Retain existing self-only reads and narrow administrative projections until the corresponding audience APIs ship; public tenant lookup exposes neither profile type. Do not widen direct `user_accounts` reads just to support search; use authorized projections without account settings, audit data, or unrelated profile/community data.

Use additive migrations for the global profile table, private labels, the three flags, and changes to join/create commands, grants/RLS, audit triggers, generated types, and tests. Backfill existing rows with the accepted defaults while preserving any already recorded explicit preferences during rollout/retry. Preserve existing curated profiles. The implemented `join_community` and optional creator-participation path do not yet accept profile fields; their current behavior must not be described as the target contract. Before enabling wider reads, resolve the relevant remaining Q-016 details and verify every authorized projection, cache, and subscription respects its audience and current preferences.

### Account-level blocking and private labels — accepted target 2026-10-15

Stable safety identity already exists as `user_accounts.user_id`. D-115 selects account-level blocking and private labels, with no public recognition ID or viewer-specific identification code. Personal DM blocks apply to the main identity across shared communities (D-086), regardless of display-name/bio edits, rejoining, or any of the three preference flags. Staff discipline remains local to the issuing community. Do not use a label, profile row, or preference as the restriction key.

Private labels let a viewer recognize an account independently of its current presentation and without requiring access to the global profile. A label may exist without a block; editing/deleting it does not block/unblock the account. Only the label owner may read, create, edit, or delete their own label through authorized operations. Community staff and the labelled account receive no label access or notifications merely from their role or involvement. Label creation/recognition uses an authorized encounter; neither labels nor a block list become a way to enumerate hidden affiliations or bypass global search opt-out. Preserve recognition across profile edits/rejoining while continuing to authorize each encountered context.

The exact label UI/text limits and access to historical labelled identities remain Q-016. D-116 settles pairwise exclusions from global search/matchmaking and direct invitations. D-118 extends host/participant exclusion to private events as well as tables, and makes removal of the counterpart's existing participation and rejection of related invitations automatic when blocking for not-yet-started resources under D-119. D-117's confirmation preview remains, with manual cancellation/denial choices only for not-yet-started non-private resources. D-119 preserves independent guest participation and leaves in-progress gatherings unaffected by the block action. True preference flags never override these rules. Ordinary community joining and participation outside the private host/participant exclusion remain available under normal rules; residual lifecycle details are Q-010. A separate main account still requires a separate abuse-prevention policy; private labels are not proof of a real-world person's identity.

### Community deactivation, reactivation, and staff pause — accepted 2026-10-14

Add `community_accounts.is_active`, boolean not null default true (D-097). New pending accounts are active but not approved. Voluntary deactivation sets false without changing `standing`; disciplinary removal sets `standing = 'removed'` and `is_active = false` together. Enforce the target invariant `standing <> 'removed' OR is_active = false`; backfill existing removed rows as inactive, with other existing rows active absent a recorded departure. There is no separate `left_at` lifecycle column in this accepted design. Preserve actor/time/reason and transition context in controlled-command audit history; the two current-state fields do not replace an action history.

| Standing | Inactive account may self-reactivate? | Result |
| --- | --- | --- |
| approved | Yes | Set active, retain approval; do not restart approval based on current auto-approval settings |
| pending | Yes | Set active, remain pending and subject to the existing approval process |
| suspended | Yes | Set active, retain suspension and its participation restrictions |
| removed | No | Explicit reinstatement by effective active same-tenant staff with `can_approve_users`; set approved/active together, preserve audit history, and do not restore staff or bookings |

New ordinary participation and DM creation/sending/receiving require an active tenant plus `is_active = true` and `standing = 'approved'`, alongside existing resource, consent, block, and capacity checks. Inactive accounts retain authenticated read-only DM history, qualifying cancelled/archived event/table history, and their own submitted reports. They lose ordinary participant access to active event/table chats and participant-based exact-address access. Independent owner/staff grants remain distinct; historical reads never confer addresses. Reactivation reuses the existing account, profile, conversations, preferences, and restrictions. It does not restore withdrawn reservations, reopen cancelled gatherings, or resume staff permissions.

Before voluntary deactivation, present a confirmation listing the caller's not-yet-started hosted/organized events and tables with safe general details, their own upcoming bookings to withdraw, and their existing guest bookings. Confirming deactivation automatically cancels the listed hosted/organized gatherings and withdraws the caller's queued/confirmed personal bookings in other not-yet-started gatherings (D-098). ## Events, tables, locations, and seats

Current direction: events and tables are distinct business concepts, clarified by the user on 2026-10-12. This replaces the proposed `activities` root and its `official_events` / `meet_play_tables` subtypes. These domains are not yet implemented in migrations. Physical fields/child tables below remain proposals where marked; championships are outside this redesign and retain their existing tentative section pending separate review.

A table is an individual scheduled game session with a fixed seat capacity. An event is a gathering that may contain zero or more tables, including gatherings without games. Recommended initial cardinality: a table stands alone or references one same-community event through nullable `event_id`; no junction table unless a concrete many-to-many requirement arises. Event attendee capacity is independent of the sum of its table seats. Organizer/host relationships are distinct from standard audit actors.

### Confirmed participation and control rules

- Events published to the community are visible to anyone viewing that community, including visitors. This does not publish invite-only events, private invitations/tables, restricted profile data, or exact private addresses. Sponsorship and audience are separate dimensions; user-published events need not be community-sponsored.
- Participating account holders must have an active (`is_active = true`), approved, non-banned same-community account in an active tenant. Current standing values are `pending`, `approved`, `suspended`, and `removed`; suspended/removed accounts are ineligible. No separate ban flag is introduced by this decision. Admission, capacity, and event registration checks still apply; paid memberships and payments do not participate in current eligibility.
- An approved account holder may register guests without registering themselves for the event or table. Guest names are optional. The sponsor is the accountable booking user and need not attend or play; sponsorship alone consumes no attendance capacity or table seat. Community/table policies and enforcement about sponsor attendance remain outside current app functionality. `tables.allow_guests` is a non-null boolean, default `true`; false prevents new guest bookings without changing existing ones. Every attending guest occupies capacity. Use one event registration per attendee and one table participation per person, with the booking account tracked separately.
- No seating at an event-associated table without approved event registration covering the people being seated, including guests. A guest-only booking must not require or create an attending registration for its sponsor. Explicitly cancelling an attendee's event registration clears that attendee's associated table reservations, including guest seats attached to the cancelled registration; registration cancellation and seat release must be coordinated atomically. Cancelling the event itself leaves all registration/participation rows unchanged. Invitation acceptance alone must not bypass registration approval or seat availability.
- Groups must be accepted together in one atomic transaction. Event registration approval and table acceptance validate every person in the submitted group and the full required capacity; accept everyone or no one. Individual records do not permit partial group acceptance, including automatic queue promotion and manual table-manager approval.
- Only organizers may add unofficial tables to their events initially; community-event moderation and private-view powers do not confer that authority. Official community-sponsored events/tables are the exception introduced on 2026-10-13: creation and all management require `can_manage_official_events`, not organizer status alone.
- Replace the proposed `can_manage_events` flag with `can_manage_community_events` and `can_manage_official_events`. The former permits staff cancellation/archival of unofficial community-public events/tables and shared hide/unhide/View Message moderation of their community-public chats under D-092. It grants no other event/table edits or organizer/table-creation powers. The latter controls official-resource creation, modification, cancellation, archival, and corresponding community-public chat moderation. Private event/table chats are excluded from staff shared moderation regardless of sponsorship, read access, or staff permissions. "Delete" uses cancellation; no hard-delete path is introduced.
- `tenant_staff_assignments.can_see_private_events` grants community-scoped visibility into private events, invitations, tables, and event/table chat messages for management awareness. It defaults false for non-owner staff and follows the existing always-true owner invariant. It grants gathering read access only, including private event/table chat bodies; this read-only oversight remains accepted after private chats are excluded from staff moderation; it grants no DM access; no posting/change/delete/participation authority. It explicitly excludes private addresses: `event_location_details` and `table_location_details` still require separate address authorization.
- `community_accounts.allow_private_invitations` is a non-null, recipient-controlled boolean, default `true`. Disabling it prevents new invitations only; existing pending invitations and accepted participation are not revoked by the preference change. Ordinary expiry, revocation, standing, and admission checks still apply to existing invitations.
- Under D-116/D-118, a block in either direction between sender and recipient prevents new direct invitations. It does not prohibit community joining or otherwise accessible participation except where a private event/table host and participant have a block in either direction. Deny that private admission through every route, including links, third-party invitations, and parent-event registration. D-118 automatically removes existing counterpart participation/requests and rejects related pending invitations for not-yet-started private resources when blocking under D-119; show mandatory effects in the confirmation. D-117's manual choices apply only to not-yet-started non-private resources. A block involving another ordinary attendee alone does not prohibit joining; guests do not inherit their booker's blocks, and in-progress gatherings are unaffected by the block action. Normal audience/approval/capacity/standing rules still apply; co-host identity details remain separate.

### Official/unofficial classification — accepted 2026-10-14

An attached table derives its official/unofficial sponsorship classification from its same-tenant parent event (D-110). Do not store an independently editable classification on an attached table. Standalone tables have their own classification. The creator's or host's staff status does not determine sponsorship; public/private audience remains separate and is not automatically inherited by this decision.

Parent-derived classification does not replace stored table lifecycle statuses or the accepted cancellation/archive cascades.

### Per-person registration and participation — accepted structure

The existing `community_accounts` key is `(tenant_id, user_id)`. Use `booked_by_user_id` and `attendee_user_id` below as the physical column names for the booking/attending community-account references discussed with the user; both use composite foreign keys with `tenant_id` to `community_accounts`, not unscoped global-user references. No new surrogate community-account ID is required. Booking responsibility is distinct from the standard audit actor fields.

| `event_registrations` field | Meaning / invariant |
| --- | --- |
| `id`, `tenant_id`, `event_id` | Stable per-attendee registration ID within one same-community event |
| `booked_by_user_id` | Required accountable booking account; may have no attending registration of its own |
| `attendee_user_id` | Nullable attending account; null means this registration represents a sponsored guest |
| `guest_name` | Optional guest display name; null for an account-holder attendee; never an identity or matching key |
| `status` | This attendee's registration state; approved before any associated table seating; exact enum remains to finalize |
| `event_registration_group_id` | Recommended nullable FK to the submitted registration group; null for an individual request |

For self-registration, booking and attending accounts match. Guests each receive their own registration ID even when unnamed; suggested display labels such as "Guest 1" are presentation only. A guest-only request creates no sponsor attendee row. Guest identities stay within their event or standalone table; no reusable guest directory or separate guest child table is needed. These fields do not grant authority to register arbitrary other account holders.

Every `table_participations` row has `id`, `tenant_id`, `table_id`, `booked_by_user_id`, `status`, and, for grouped requests, a recommended `table_participation_group_id`. Its occupant comes from exactly one of two paths:

- Event-associated table: `event_registration_id` is required and references this person's registration in the table's own event and tenant. Take attending account/guest name from that registration; do not duplicate them in the participation. Keep the participation's booking account consistent with the registration's booking account. A registration can be referenced by multiple tables in the event, but only once per table; any schedule-conflict rule is separate.
- Standalone table: `event_registration_id` is null; `attendee_user_id` and nullable `guest_name` identify the person directly using the same account-holder/guest rules. The booking account remains separate and need not occupy a seat.

Group records and nonattending sponsors consume no capacity. There are no seat offers, response deadlines, or offer/payment holds in the initial implementation. A host's organizing authority does not by itself establish whether they are playing or occupy a seat. Separate numbered-seat records are unnecessary unless actual seat positions become a requirement.

### Atomic group acceptance

Persist group membership so confirmation cannot select a convenient subset. The recommended group records above have same-tenant/resource/booking-account constraints on their member rows. A group is a particular submitted request, not every booking ever made by its sponsor. Event registration groups and table participation groups are separate: approved event attendees may choose different tables or no table at all.

Lock the group and relevant registration/capacity rows, validate every member's current eligibility and, for event-table seating, their event approval, and check capacity for the full group before committing confirmation. Withdrawn, cancelled, and rejected requests cannot be promoted. On failure no member becomes newly approved/confirmed and no capacity is consumed. Serialize edits, withdrawal, manager decisions, and automatic promotion; stale request revisions and retries must not confirm an old group or restore a terminal request.

Cancelling one attendee's event registration releases that attendee's linked table participations; an explicit group cancellation covers all selected registrations and linked seats in one transaction. A sponsor's own registration is not a parent of their guests' registrations.

### Automatic and manual seat confirmation

`tables.manually_confirm_seats` is a non-null boolean with default `false`. Both configurations are in the initial scope:

- False: handle reservation requests immediately in receipt order, subject to current eligibility and capacity. Automatically confirm the earliest eligible whole group that fits and has not withdrawn. Queued groups are reconsidered when relevant capacity or eligibility changes.
- True: authorized table managers review queued requests and may approve, reject, or notify the booking account about an issue as they see fit. Manager selection is discretionary; approving a chosen group must still satisfy same-tenant/event eligibility, full capacity, and atomic group confirmation. Capacity becoming available alone does not auto-approve a manual table.

Switching an existing table from manual to automatic confirmation requires a confirmation modal explaining that queued requests will be processed automatically in receipt order as eligibility and available seats allow. **Continue** triggers the switch to `manually_confirm_seats = false` and processes the existing queue using the same whole-group allocation rules as new automatic requests. Preserve current queue timestamps, including any reset by an earlier group addition; skip groups that do not fit without splitting them or changing their priority. **Cancel** closes the modal and leaves `manually_confirm_seats = true`; opening or dismissing the modal performs no mutation or confirmation. See the [frontend interaction plan](05-frontend-patterns.md#forms-and-seat-actions) and [transaction plan](06-backend-patterns.md#confirmation-modes-and-group-transactions).

A successful approval/automatic promotion is final confirmation. The booking account does not need to accept it again. No current seat-offer state, response/claim deadline, reservation expiration timer, or payment window exists. Optional recipient-confirmed offers may be designed later; they are not a dependency of this version. Registration approval for the parent event still precedes event-table seating; this table flag does not redefine event-level organizer approval.

Rejection removes the complete rejected request from all active queue queries and future promotion. Preserve rejected per-person records and decision history rather than erasing the evidence needed for the registering user. Record the rejecting global user, server decision timestamp, and optional reason for the request/group revision. A new attempt requires an explicit new submission/revision and new queue timestamp; reusing lifecycle rows must preserve prior immutable decisions. An issue notification leaves the request pending and creates no response deadline or implicit rejection.

Publish approval/rejection decisions to the booking account promptly when the transaction commits. Rejection notices include the timestamp, rejecting user's safe display identity, and reason when supplied. Use a narrow authorized decision projection, not general staff profile/email access. The notification and decision must be durable together; no notice may claim success before commit. External delivery channels remain separate implementation choices.

### Pending-group edits

| Edit | Accepted behavior |
| --- | --- |
| Add/correct an optional guest name | Keep the request's queue position; this does not change seat demand. |
| Remove someone from a waiting group | Reduce requested seats and keep the remaining group's queue position; removing everyone withdraws the request. |
| Add someone to a waiting group | Give the enlarged group a new server queue timestamp. Explain the loss of the old priority before saving; revalidate new guest eligibility and `allow_guests`. |
| Change a group with a seat offer, if that future option is introduced | Revalidate the offer and its reserved capacity; an old offer must not confirm the previous group. This is a deferred compatibility rule, not a current offer workflow. |

Apply edits transactionally to the group and affected per-person rows, increment the request revision, and re-evaluate the current group's eligibility/capacity. Automatic tables may confirm the edited group when its queue turn and capacity allow; manual tables still require a manager's decision. No stale approval may accept only the old membership. A name edit alone does not reset queue priority or create an extra seat.

### Queue order when groups do not fit

The standard automatic policy is first-come, first-served among eligible queued requests that fit available capacity. Scan in current queue order and select the earliest whole group that fits. Skip groups that need more seats, preserving their queue position and pending state; do not split or cancel them. Voluntary additions reset priority under the edit rules above; being skipped does not.

After each atomic confirmation, recalculate available seats from confirmed occupancy. Store server-assigned queue time with a stable tie-breaker (recommended: queue time plus request/group ID). New arrivals must not bypass an earlier eligible request that fits. Ordinary standing and event-approval checks still apply, with no payment or membership checks.

For example, with three seats available and queued groups needing four, two, and one seats in order, automatically confirm two, then one. The four-person group retains its position and is reconsidered when enough seats become available. Do not prefer a later fitting group merely to maximize occupancy. Manual tables can show this queue ordering to managers, but their explicit approve/reject/issue-notification decisions govern confirmation.

### Disabling guests and removing existing bookings

Changing `tables.allow_guests` to false changes the rule for new bookings only. It does not modify existing participations, groups, or event registrations, and does not release capacity. Existing requested/waitlisted/confirmed bookings continue under their ordinary rules; the changed flag alone does not invalidate them. Creating a new guest participation or resubmitting a cancelled/rejected one requires the flag to be true. An existing event registration alone does not authorize a new guest booking at a table that now disallows guests.

When an authorized table manager disables guests, the UI identifies which current table bookings are for guests and offers an optional selection interface to remove them. Keeping all bookings or dismissing the prompt changes none of them. With no guest bookings, show that fact and no removal action. The standard table-management UI always supports explicitly removing guest bookings, regardless of the current flag. See the [frontend interaction plan](05-frontend-patterns.md#table-guest-management).

Removal is a separate, explicit table-management command targeting selected `table_participations`. Preserve cancellation history and release their seats through the normal lifecycle. For event-associated tables, do not cancel the referenced `event_registrations` or the guest's reservations at other tables; event-attendance cancellation is a separate action with broader consequences. Explicit cancellation of selected people is compatible with atomic group acceptance: revalidate affected pending groups under the applicable automatic/manual mode without confirming a stale group or cancelling unrelated attendees. The flag edit itself never triggers this cleanup.

### Permission and preference ownership

The proposed staff additions are `can_manage_community_events`, `can_manage_official_events`, `can_manage_community_permissions`, `can_see_private_events`, `can_handle_reports`, and `can_manage_settings`; all default false for non-owner staff and remain true for owners. `can_manage_events` is a superseded proposal, not an additional retained flag. For unofficial community-public events/tables, the organizer or staff with `can_manage_community_events` may cancel/archive. Private organizers retain management of their own unofficial resources; neither public cancellation/archive authority nor private-view permission grants staff private event/table data or lifecycle writes. D-092 permits chat hide/unhide/inspection only for community-public event/table chats with the matching management flag; private chats have personal controls only, with existing read-only oversight retained. Ordinary official-resource creation/modification/cancellation/archival requires active staff with `can_manage_official_events`, even when someone else is recorded as organizer. The narrowly scoped deactivation and owner community-archival commands additionally perform their required automatic cancellations under D-098/D-101; they grant no general official-resource editing authority. `can_post_public_events` remains a participant permission on `community_accounts`, default false; `can_manage_community_permissions` grants/revokes participant permissions, not staff permissions or self-escalation. D-106 adds removal/revocation flags and renames the assignment grant to `can_grant_staff`; editing individual permission values remains owner-controlled. D-109 narrowly authorizes disciplinary removal's unofficial-gathering cancellations while excluding official resources from that flow.

Private event sharing requires no special posting permission. The recipient's `allow_private_invitations` preference is self-controlled and must have a separate authorized update path from staff-controlled participant permission grants. Staff grants remain separate from participation approval, but active non-owner staff require an active community account. Owners remain exempt; any staff member wishing to participate must satisfy ordinary participation rules.

### Event cancellation and archival — accepted rules

These rules apply identically to events and tables (confirmed 2026-10-13). Neither resource is hard-deleted. An explicit Cancel Event/Table action records cancellation; Archive Event/Table is a separate explicit action, never an automatic consequence of elapsed time. A directly requested Archive action is allowed only when the resource is cancelled and either it had zero registration/participation rows of any status at cancellation, or it has remained cancelled for at least 30 days. Withdrawn/rejected rows count as prior registrations/participations. Capture the zero-row condition at cancellation; later row changes and retries do not reset eligibility or the cancellation clock. An authorized parent-event cancellation/archive action also cascades its lifecycle to attached tables as specified below; no separate child action is required. No reopening/unarchiving ships initially; a replacement gathering requires fresh bookings.

Cancelling an event sets each attached table's stored status to `cancelled`, except tables already `archived` remain archived (explicit user clarification, 2026-10-13). Archiving an event sets every attached table's stored status to `archived`. This supersedes the earlier inherited-unavailability-only recommendation. Event/table status changes block new registrations, invitations/acceptance, table bookings, approval, queue promotion, and allocation-triggering mode switches. Independently cancelling/archiving a table affects neither its parent nor sibling tables. Never convert child tables to standalone tables as a side effect. The event and table resource rows change; all `event_registrations` and `table_participations` rows remain unchanged, including audit timestamps. Explicit cancellation of a person's registration remains the separate operation that releases that person's linked seats. Exclude unavailable gatherings from upcoming activity, actionable queues, reminders, and recommendations without treating preserved bookings as no-shows.

Recommended physical fields on both `events` and `tables`: `cancelled_at`, `cancelled_by`, optional `cancellation_reason`, a protected snapshot such as `had_bookings_at_cancellation`, plus `archived_at` and `archived_by`. The snapshot considers all directly associated registration/participation rows, irrespective of status. A parent cancellation that newly cancels a table records its actual cancellation time, initiating user, parent cause/reason, and that table's own booking snapshot; do not copy the event's booking count. Preserve existing cancellation metadata on already-cancelled/archived tables and existing archive metadata on already-archived tables. Parent archival records the transition for tables newly archived, without overwriting cancellation history. Use server instants and global-user actor references, retain parent-action attribution, and make retries idempotent. Keep organizer/host relationships after cancellation/archive, independently of `created_by`.

### Cancellation and archive visibility

The final user instruction of 2026-10-13 supersedes staff-only archival visibility and the earlier chat-access cutoff. A historical registration/participation row grants its account holder access to the corresponding cancelled or archived event/table, regardless of that row's requested, waitlisted, confirmed, withdrawn/cancelled, or rejected state. For guest rows, the registering account (`booked_by_user_id`) receives this access; guests receive no login, invitation to the community, or separate access mechanism. The grant is resource-specific: event registration is not a blanket grant to every child table/chat. Existing platform/account/tenant restrictions remain separate from registration status.

| Resource / audience | Cancelled visibility | Archived visibility |
| --- | --- | --- |
| Unofficial community-public event/table | Anyone, including anonymous visitors, through a Cancelled filter and safe public detail; organizers, historical registrants/participants, and guest bookers retain access | Former organizers, historical registrants/participants, guest bookers, and same-community staff |
| Unofficial private event/table | Original organizer/invitee audience plus historical registrants/participants and guest bookers; authorized private-view staff retain oversight | Former organizers, historical registrants/participants and guest bookers; other staff require `can_see_private_events` rather than staff status alone; invitation alone is insufficient |
| Official community-sponsored event/table | For community-public resources, anyone including anonymous visitors, plus historical registrants/participants and guest bookers; private details stay protected | Same-community staff plus historical registrants/participants and guest bookers; organizer status alone is not a non-staff exception for official resources |

Anonymous visitors may read cancelled community-public events and tables, including safe listings/details and the Cancelled filter. Cancellation does not expose private resources, chat, registrant/guest lists, or exact private addresses, and grants no anonymous archive access. Private visibility checks remain applicable if an official resource is private; official-management permission alone does not imply private-view or exact-address access. Show the Archived filter to eligible organizers, historical registrants/participants, guest bookers, and staff, returning only authorized records. Apply these rules to direct links, feeds, child-resource joins, APIs, and Realtime. For archived-parent tables, resolve historical access using the table's own relationships without exposing unrelated child tables or privileged parent fields; parent linkage must not deny an otherwise permitted table history merely because its booking was withdrawn earlier.

### Cancelled and archived chat and addresses

Cancellation of an event immediately makes its event chat and attached table chats read-only; independent table cancellation affects only that table's chat. Historical registrants/participants, registering accounts for guests, organizers, and authorized staff retain resource-specific reads. Anyone entitled to see the archived event/table retains read-only access to that resource's chat indefinitely. No current confirmed-seat requirement or archive-age timeout may erase this historical grant. A public listing or private invitation without a qualifying chat relationship does not expose cancelled chat. Event chat is now explicitly MVP alongside table chat; active event access uses approved event registration, not a table seat.

Participant-based exact-address access ends immediately on table/event cancellation, even though a confirmed participation row remains stored. Archived/history/chat access never restores it. The organizer retains their existing, independently authorized location-management access where applicable after cancellation/archival (accepted 2026-10-13). This means an authenticated user inside the app acting as organizer/location manager, not an outside venue owner or guest; no new location-manager role, external identity, or guest access system is introduced. Preserve only the specific location access the organizer already held, not every private address connected to an event. Add no general staff address exception: none of `can_see_private_events`, `can_manage_community_events`, or `can_manage_official_events` grants exact-address access by itself. A staff user acting as an independently authorized organizer is checked through that same organizer/location relationship.

### Cancellation notifications

The complete cancellation-notification policy was accepted on 2026-10-13. Notify queued/confirmed account holders and guest bookers, organizers/affected child-table hosts, and pending actionable invitees. Withdrawn/rejected rows alone grant history access but do not trigger an alert; unrelated staff receive no broadcast. Aggregate a parent-event cancellation into one notice per affected user covering their tables and guest bookings. Include community, title/scheduled time, cancellation timestamp, cancelling user's safe display identity, optional reason, and an authorized link; exclude addresses, chat previews, and other users' guest lists. No additional alert is sent solely for archival. Retain the cancellation notice, with details/history access determined independently when opened. Use the in-app inbox first, durable deduplicated retries, and suppression of obsolete reminders; email/push remain separate decisions. See the [accepted backend notification policy](06-backend-patterns.md#cancellation-notification-policy).

Anonymous cancelled-public visibility and parent-to-table cancellation/archive cascades are settled. Already archived children are never downgraded by parent cancellation. Direct table archival continues to use its own cancellation/eligibility rules; parent archival cascades as part of the authorized event action.

### Event and table chat — MVP

`event_messages` and `event_chat_lifecycles` are part of the proposed schema, matching `table_messages` and `table_chat_lifecycles`. Each event has its own chat even with zero tables; an event's chat and each child table's chat are distinct audiences and histories. Use concrete same-tenant parent foreign keys rather than an unchecked resource-kind/resource-ID pair.

Event-chat access mirrors table chat: while active, approved event registrants and the organizer have the corresponding participant/organizer chat access. An event registration is sufficient; a table seat is not required. Private-view staff may read private event chat under `can_see_private_events`, but the flag alone does not permit sending. Public discovery, invitation alone, and guest sponsorship without the booker's own approved registration do not independently grant active participant chat access. Historical guest-booker access after cancellation/archive follows the already accepted rule.

Cancellation immediately makes the event chat and affected child-table chats read-only; independently cancelling a table affects only that table's chat. Archived event viewers retain read-only event chat indefinitely, just as archived-table viewers retain that table's chat. Event access never grants every child chat. The parent lifecycle remains authoritative even if a cached lifecycle row is stale. Active/completed gathering chat windows remain an open policy decision; the cancelled/archived retention rule is settled.

Recommended common message fields are parent FK, `author_user_id`, bounded text `body`, trusted ordering/timestamps, and `client_message_id`, in addition to standard audit fields. Personal visibility preferences and staff moderation state belong to the separate relations described below. Author identity is derived from the authenticated sender and checked against the concrete resource; staff organizer authority is separate from community participation. Scope deduplication to tenant/parent/author/client-message ID. Read and send permissions are independent, with no exact-address grant from either.

### Message limits — accepted

The initial limits apply to direct messages, event chat, and table chat (D-093). A message may contain at most **5,000 characters**, including line breaks. Reject empty or whitespace-only bodies. Reject overlength bodies with a clear explanation and preserve the draft; never silently truncate. Enforce the same limit in the UI and trusted send path.

Allow at most **30 messages per minute per main user account**, combined across communities and chat types. Also limit initiating contact to **10 new DM recipients per hour**. Enforce that recipient budget against the main account so changing communities or opening another device cannot reset it. Message-size and rate limits do not replace standing, consent, block, or resource-send authorization.

Recommended implementation details: measure characters as Unicode code points, consistently with the report-gap length convention; line breaks count and whitespace-only validation does not silently rewrite otherwise valid content. Use server time and rolling windows, with atomic shared accounting for concurrent sends. Count a committed message once, including across retries with the same idempotency key; denied/failed sends do not become successful-send usage. For the new-recipient budget, the recommended definition is a distinct main-account peer with no prior committed DM history with the sender in any community, charged on the first successful send rather than opening the composer. This abuse-budget definition is separate from the later community-specific conversation-request rules. Physical counter storage is an implementation choice; short-lived rate-accounting records are not retained chat history, and cross-community contact metadata must not be exposed to community users/staff.

### Personal message hiding and event/table moderation — accepted

Personal **Hide for me / Unhide for me** controls apply to DMs, event chat, and table chat. An authenticated user changes only their own message-view preference; other authorized viewers are unaffected. Staff have no authority to change another person's preferences. A staff user who independently participates in a DM may use the same personal controls for their own view, with no moderator power over that conversation. No staff permission, including `can_handle_reports`, grants shared hiding or a hidden-body moderation override in DMs.

Only **community-public event/table chats** support staff **Hide for everyone / Unhide for everyone**. An active same-tenant staff assignment needs `can_manage_community_events` for unofficial resources or `can_manage_official_events` for official resources, determined from the actual message parent. Organizer/host status alone does not confer this staff moderation power. Private event/table chats use personal hide/unhide only: even staff with management permissions and a right to read the chat cannot hide/unhide for others or use the moderator View Message action. This supersedes the earlier private-chat-read-plus-management rule. Existing `can_see_private_events` read-only oversight is explicitly retained; staff can read private chats through that grant and change only their own view preferences. Community-public describes the event/table audience, not anonymous access to chat bodies.

In community-public event/table chats, a moderator hide suppresses the body for all ordinary viewers, including the author and other staff. Only staff meeting the matching management permission and current community-public scope checks may use **View Message** to inspect the retained body privately without unhiding and rehiding it. This is a separately authorized read, not a visibility-state change. It grants no access to other messages, private-chat moderation, DMs, or addresses. Existing private-view/report-handler authority alone does not grant this inspection.

Keep personal preferences, shared moderation state, and canonical content separate. Recommended physical tables (standard audit columns still apply):

| Proposed table | Fields and invariant |
| --- | --- |
| `direct_conversation_message_hides` | Unique tenant/conversation/message/viewer; composite FKs to the same conversation's message and participant. Row presence means hidden for this viewer; only that authenticated participant manages it |
| `event_message_hides` | Unique tenant/event/message/viewer; same-tenant message/parent FKs, viewer FK to global `user_accounts`. Only the viewer with current authorized event-chat reads manages their preference; an authorized owner viewer need not have a community account; active non-owner staff must satisfy D-105 |
| `table_message_hides` | Table equivalent with same-tenant message/parent FKs and self-only viewer state |
| `event_message_moderations` | At most one row per event message, with matching tenant/event/message FKs; `is_hidden`, recommended revision for concurrent commands, and trusted audit actors/times. Shared moderation applies only to community-public chats; private chats have no active shared override. Missing row means visible; retain changes in `tenant_admin_actions` |
| `table_message_moderations` | Table equivalent; shared moderation requires this table to be community-public plus its matching official/unofficial staff flag; private tables are excluded |

Personal Unhide removes only the caller's hide-preference row; it never deletes or rewrites the source message. Staff Unhide changes only shared moderation state and leaves all personal hide choices intact. There is no DM shared-moderation table, and event/table shared moderation cannot apply to private chats. These operations preserve message IDs, authorship, original body, chronology, report snapshots, and gap metadata.

Ordinary display requires existing chat-read authorization and an absent personal hide; community-public event/table chats additionally require no moderator hide. Private event/table chat display uses personal controls only. Personal Unhide cannot override a moderator hide. Recommended UI uses recoverable placeholders so the appropriate Unhide controls remain reachable. A moderator's View Message preview leaves both layers unchanged. Neither layer creates a new right to read a resource, except the scoped public-chat moderation authority stated above.

Enforce shared suppression in backend message projections and delivery: do not send moderator-hidden bodies to ordinary clients through raw-table queries, joins, pagination, search, quoted previews, notifications, or Realtime. Restrict canonical-body access behind authorized read commands/projections and use a separate checked View Message path. Send visibility invalidations so clients remove newly hidden bodies from active views/caches; hiding cannot recall content already seen or copied. Personal preferences are self-only and must not be broadcast to others.

Users with retained cancelled/archived or suspended/removed read-only history may still manage their own view preferences. Authorized staff may moderate retained community-public event/table chat messages; private chats remain excluded even after cancellation/archive; read-only lifecycle restrictions still prohibit new chat posts and content edits. Permanent historical retention preserves the source message rather than guaranteeing its body is always displayed. Report evidence is independently authorized and permanently retained: hiding/unhiding does not change selected text, exclude intervening messages from gap calculations, or erase resolution/history records.

### Community direct messages — accepted scope and proposed structure

DMs are MVP (2026-10-13). Both sender and recipient must have active (`is_active = true`), approved community accounts in the conversation's active community. A global account or staff assignment alone is insufficient, including for an owner without a community account. Guests have no DM identity. Conversations and their children retain one immutable `tenant_id`; the same people in different communities have separate conversations and histories. Ordinary DM reads are participant-only; event/table management and private-view flags grant no DM access.

Group DMs are a known future requirement. **Accepted structure (2026-10-13):** use general conversation and participant tables now, with the initial one-to-one behavior enforced by the UI and server API until group DMs are implemented. Do not encode the feature limit as a conversation kind, stored participant pair, or database participant-count constraint/trigger. The prior fixed-pair and kind-based proposals are superseded. Retain separate event/table chat roots.

| Proposed table | Fields and invariant |
| --- | --- |
| `direct_conversations` | `id`, immutable `tenant_id`, and standard audit fields; no `kind`, canonical participant-pair columns, or tenant/pair uniqueness constraint. Participants are represented only by child membership rows |
| `direct_conversation_participants` | Unique `(tenant_id, conversation_id, user_id)`; composite FKs to conversation and `community_accounts`. Authoritative conversation membership, preserved for historical authorship/access. The schema supports multiple participants without a two-person count constraint or trigger; membership writes require authorized server commands |
| `direct_conversation_messages` | Same-tenant conversation FK, `author_user_id` referencing its participant row, bounded plain-text `body`, stable server `message_sequence`, `client_message_id`; personal hiding uses separate viewer rows, with no staff-controlled shared moderation/redaction state; trusted author and retry deduplication |
| `direct_conversation_user_states` | Unique tenant/conversation/user referencing its participant row; private last-read cursor and `is_muted` boolean not null default false. Mute lasts until explicitly changed. Inbox archive state, if exposed, affects only this user. These rows cannot grant membership or change another person's history; notification reconciliation must prevent replay of a muted backlog |

Existing `community_accounts` use `(tenant_id, user_id)`, with `user_id` referencing the main `user_accounts` identity. Preserve matching tenant/conversation keys throughout. Database constraints enforce referential integrity, community consistency, and unique membership rather than conversation size. Authorization uses participant rows plus current standing/consent/block rules. Community suspension/removal changes standing without deleting participants or their message authorship.

The initial UI selects one recipient. The server create-or-get API accepts `tenant_id` and one `recipient_user_id`, derives the sender from authentication, and resolves the continuing thread for those identities in that community. Creating a missing thread validates distinct approved accounts and recipient controls, then atomically creates the root plus sender/recipient participant rows. Existing-history reads use their separate authorization predicate, so a send restriction must not prevent authorized read-only reopening. Reject multi-recipient or caller-supplied membership overrides at the API boundary. Do not expose add/remove/replace-participant operations until group membership rules are implemented. Database grants/RLS deny direct client conversation-creation and membership writes that would bypass these commands; this is an authorization boundary, not a schema-level participant-count limit. A transactional RPC may implement the server command without adding a count constraint or trigger.

**Accepted conversation identity (D-095):** the same two main user identities have one continuing DM conversation within each community, regardless of which person initiates. Opening a new composer, personal inbox archival, blocking/unblocking, logout, or rejoining with the same main identity must not create another thread. These operations do not bypass current read/send restrictions. Different communities still have separate conversations and histories.

Prevent duplicate concurrent creation in the command: serialize requests for the tenant plus normalized sender/recipient IDs, then find the conversation with exactly that participant set or create it in the same transaction. That transient lookup/locking key does not become pair columns or a two-person schema invariant. Every creation path must use the same transaction protocol; test simultaneous requests initiated from opposite ends as well as retries. The physical locking mechanism remains an implementation detail. Creating a missing thread only on the first successful message remains a recommendation, not an accepted timing decision. Future group membership rules must separately define thread identity/reuse rather than treating this one-to-one decision as a unique-membership-set rule for groups.

Use a unique send key `(tenant_id, conversation_id, author_user_id, client_message_id)` and unique ordered `(tenant_id, conversation_id, message_sequence)`. Sequence allocation and commit visibility must support consistent history/report snapshots; do not assume there can be no numeric gaps or count omitted messages by subtracting sequence values. Read cursors must belong to the same conversation and remain private. Personal inbox archival hides only that user's thread; it does not delete shared history. Gathering cancellation/archival does not alter a DM conversation.

**Later group implementation:** conversation and message IDs can remain unchanged, and the participant table already permits larger memberships. Add authorized group creation/membership operations and UI when their rules are ready. Membership history, join/leave/rejoin periods, roles, invitation/request records, earlier-message access, and send eligibility when someone is suspended/opted out/blocked still need design. Recommend creating a new group when expanding a one-to-one discussion, rather than exposing earlier private history to a newcomer. A future conversation kind is optional only if distinct product semantics justify it; none is required for the initial size limit.

### Accepted DM policies and deferred features

- **Standing:** inactive, pending, suspended, and removed community accounts cannot create conversations, send, or receive new DMs. Both endpoints must be active and approved in an active tenant. Inactive, suspended, and removed accounts retain read-only access to their existing conversation history; this does not grant access to other threads or waive authentication. Pending status has no newly granted historical-read entitlement. Keep history reads separate from send authorization, and preserve referenced community accounts/participants.
- **Recipient controls:** add `community_accounts.allow_direct_messages`, boolean not null, default true, controlled by that account holder. False stops new incoming DMs even in existing conversations; it does not erase history or itself prohibit that user from sending to a consenting recipient. Keep it independent of `allow_private_invitations`. Blocking prevents new DMs in both directions and preserves history.
- **Future requests:** conversation-request approval comes later, scoped to the sender's community account and the receiving community account. A sender with no prior DM history with that recipient must then be approved first. History in another community must not bypass approval. Do not require requests or add speculative request-state tables to the initial implementation. Define qualifying prior history (including group history), repeat requests, and revocation when implementing it.
- **Privacy and moderation:** report and block are in the initial DM implementation. Ordinary access remains participant-only. Authorized reviewers receive selected evidence and the accepted gap metadata below, not unrestricted conversation reads. Report viewing and lifecycle handling use `tenant_staff_assignments.can_handle_reports`; reporters can also read their own reports. Existing event/table flags confer none of this authority.
- **Content:** plain text initially. Attachments, sender editing, and sender deletion are deferred. Personal inbox archival must not delete the peer's conversation. Report records and related evidence are retained permanently. DM hiding/unhiding is personal only; staff cannot alter shared DM visibility. Community-public event/table shared moderation uses the scope-specific management flags and cannot erase or rewrite report evidence. Private event/table chats permit only personal hiding; read-only staff oversight remains.
- **History and read state:** retain ordinary DM history with no automatic expiry (D-096), supported by usage monitoring and budget thresholds. Do not introduce a message TTL or age-based purge. Personal inbox archival, hiding, blocking, muting, or community suspension/removal does not expire history or enlarge its authorized audience; suspended/removed participants retain their accepted read-only access. Threshold alerts prompt operational review, not automatic history deletion. Private unread state is required for the accepted DM notification/mute behavior; shared read receipts and typing indicators remain deferred. D-097–D-103 settle community deactivation, standing-preserving reactivation, retained inactive/archived-community history, staff pause, and gathering cancellation; global account deactivation/closure/deletion/anonymization remain deferred.

### DM notifications and muting — accepted

DM delivery starts with **in-app notifications enabled by default**; email and device push remain later decisions (D-094). The notice contains community, sender, current unread count, and a conversation link, with no message-body preview. Keep at most one active unread notification for each recipient/conversation and update it as messages arrive. Completed/read notification history must not become a second active unread entry.

Avoid an additional alert when the conversation is focused and the new message is actually displayed to that recipient. A background tab, merely opening the conversation, or reading an older page does not automatically mark new messages read. Use recipient-owned read state and actual display acknowledgments; do not publish read receipts to the sender.

Muting is private to one user and one conversation in its community. It lasts until manually unmuted; timed mutes are deferred. Messages continue to arrive, persist, and display. Suppress DM notification-inbox entries, toasts, sounds, and contributions to the main notification badge for that muted thread, while retaining its unread indicator in the conversation list. Muting is independent of personal message hiding, receiving consent, blocking, and another community's conversation with the same peer. Do not disclose mute state to the peer.

Unmuting resumes alerts only for subsequent messages; it must not replay the backlog or revive stale queued alerts. Recommended reconciliation: mute suppresses any active unread DM notice and invalidates pending alert work; unmute alone does not restore that notice. A later eligible message may create/update one notice showing the current unread count, without issuing separate alerts for older unread messages. Atomic upsert/deduplication and current-state checks must handle sends, reads, mute/unmute, worker retries, and multiple devices. The inbox badge counts eligible notices rather than all conversation unread markers. These rules concern DM-message alerts, not unrelated cancellation or report notifications.

### Account-based blocking and discipline

Accepted: block targets and all community disciplinary targets use the stable main `user_accounts.user_id`, not a profile, display name, email, or disposable community-account identifier. Rejoining, changing either profile, editing private labels, or toggling `show_global_profile`, `user_is_discoverable`, or `enable_matchmaking` must not evade an existing restriction. Community-account standing already uses that global user ID together with its tenant; do not replace this with an identity disconnected from the main account. This protects against rejoining with the same main account, not creation of an unrelated global identity. D-115's private labels do not change this internal identity or grant users/staff access to hidden profiles.

**Accepted enforcement scope (2026-10-13, extended 2026-10-15 by D-116–D-119):** account-level blocks apply across communities and global features. Staff discipline remains limited to the community issuing it, keyed by `(tenant_id, subject_user_id)`, and follows that main account if the user rejoins. Global identity does not grant global staff authority. The proposed `user_account_blocks` has no tenant in its identity key. Evaluate either directed block row as a restriction between the pair; one person's unblock does not clear the other person's block.

| Interaction between A and B, with a block in either direction | Block effect |
| --- | --- |
| Standard global account search | A does not find B and B does not find A; do not remove either account from unrelated users' eligible searches |
| Global matchmaking | Do not propose or form a match containing both accounts; each remains eligible with other users under their own `enable_matchmaking` and ordinary eligibility rules |
| Direct invitations | Neither can directly invite the other, regardless of which user placed the block or whether an invitation preference is enabled |
| Community DMs | Preserve D-086: deny new conversation creation/sends in both directions across every shared community; retain authorized history |
| Joining a community | A personal block is not a joining prohibition in either direction, including a community owned or managed by the other user; community approval/standing still applies |
| Manually joining events/tables through other permitted means | A block alone does not prohibit participation or co-presence for either user; normal audience, admission, and capacity checks still apply, subject to D-118's private event/table host exception |
| Joining a private event or table hosted by the other account | Deny if either host blocks participant or participant blocks host. Determine privacy from the resource's audience and host/organizer from its actual hosting relationship, not community ownership, staff status, or audit authorship |
| Existing participation/invitations for not-yet-started private events/tables hosted by either account | On block confirmation, automatically withdraw/remove the counterpart's current participation/requests and reject related pending invitations in both host directions; show every mandatory consequence beforehand. D-119 excludes in-progress resources and preserves independent guests. Do not offer a Keep option |

Private-event/table admission must enforce the host/participant rule through every joining path and recheck before acceptance/confirmation, including queued/manual approval and event-associated tables. Event registration does not bypass a private child table's admission rule; third-party invitations or links do not bypass it either. For atomic groups, validate each actual identified participant against the host before confirming the whole group; never substitute a guest's sponsor/booking account for the attendee. A guest-only group may qualify despite a host/booker block, while a group still containing an ineligible account attendee must be edited before atomic acceptance. A block between ordinary participants does not turn into a host veto. D-118 supersedes the earlier exclusion of private events from this rule. Non-private resources retain ordinary admission rules, and a shared third-party private resource is not automatically affected merely because both accounts attend.

D-119 settles guest independence: a block applies to the two accounts, not to their guests. Guests may join or remain without the blocked/blocking sponsor attending, including in the other account's private event/table when ordinarily eligible. Removing the sponsor's own participation preserves guest registrations, seats, group/booker links, and normal processing of surviving guest requests. A block against the booker alone is not a guest admission veto or a reason to cancel guest participation. Preserve separately authorized guest-booking management without granting the sponsor attendance or bypassing direct-invitation/DM restrictions.

| Proposed table / existing relationship | Fields and invariant |
| --- | --- |
| `user_account_blocks` | Directed, unique `(blocker_user_id, blocked_user_id)`, both FKs to `user_accounts`, distinct users, trusted audit fields; only blocker manages own row. Either direction enforces D-116/D-118's pairwise global search/matching, direct-invitation, DM, and private-event/table host/participant restrictions. The block command applies D-118's mandatory private participation/invitation changes within D-119's not-yet-started, actual-attendee scope; no tenant-specific duplicate is required |
| `community_accounts` + `tenant_admin_actions` | Preserve standing and disciplinary history against tenant + main user identity. A later suspension/removal/reinstatement command must retain the restriction across rejoin attempts and tenant auto-approval, and audit actor/reason/time. Extra sanction tables are only needed when sanction duration/types require them |

Personal block lists are not a public directory or a staff-readable global relationship graph. Authorization may check either direction without exposing either person's other blocks. Search/match exclusions are pair-specific, not global account suspension. D-118/D-119 mandate private host/participant removals and invitation rejection only for not-yet-started resources; D-117's manual handling likewise excludes started resources and remains non-private only. Guests remain independently eligible, and the block action does not alter in-progress participation/access. Unblocking does not restore cancelled participation, rejected invitations, discarded sends, or cleared requests; any later joining/inviting must be new and currently authorized. No community removal, whole-resource cancellation, or eviction of unrelated participants follows from blocking. Existing match records, co-hosts, historical/shared-chat details, Discussion, and competitions retain residual questions under Q-010.

Owner protections prohibit administrative removal/suspension or denial of tenant-management access. A personal DM block grants no such authority and must not be bypassed because the blocked person is an owner/staff user. Reviewers may take only separately authorized disciplinary actions within their tenant.

### Block confirmation and existing participation — accepted 2026-10-15

When initiating a block, show a server-derived preview of relevant existing participation/requests and pending invitations involving the target. D-118 divides the prompt into mandatory private-resource consequences and optional non-private actions; D-119 limits both sets to not-yet-started resources. Show safe resource/community, time, status, direction, and linked-seat/group effects within the caller's authorized audience; the preview is not a directory of the target's private activities. In-progress events/tables, including their existing participation, pending requests/invitations, and authorized access, are unaffected by triggering the block. Completed/cancelled/archived attendance and historical records are likewise preserved. Determine not-yet-started from live lifecycle and `starts_at >` trusted confirmation time, not the time the preview opened; exclude a resource that starts before confirmation and refresh the preview.

For not-yet-started private events/tables hosted by the target, inform the caller that their own participation/requests will be automatically withdrawn/removed and related pending invitations rejected. For not-yet-started private events/tables hosted by the caller, list where the target's participation/requests will be automatically removed and related invitations rejected. These are mandatory effects of confirming the block in both directions, including previously confirmed participation in those upcoming resources; no Keep option is offered. The actual private host/participant relationship determines scope, even if a third party sent the invitation. The rule also prohibits subsequent re-entry/new invitations along that relationship while either block remains. This narrowly authorized block transition grants no general organizer/staff power and cancels no gathering itself.

Manual per-item cancellation/denial controls in the block interface apply only to not-yet-started non-private events/tables and related invitations. Offer the caller's own withdrawal, authorized management cancellation/denial, or invitation decline/revocation as appropriate. Start optional choices unselected, and allow confirmation without selecting any; mandatory private consequences still apply. A co-attendee cannot remove the target from a third-party gathering merely by blocking them. Shared third-party private gatherings with neither user as host are outside automatic host-based removal and receive no manual cancellation controls in this block interface; ordinary authorized management/withdrawal elsewhere is unchanged.

Stage all choices and show all mandatory consequences before final confirmation; cancelling/dismissing the prompt makes no changes. Confirmation applies the block, all mandatory private removals/invitation rejections, and selected authorized non-private actions consistently. An event-registration withdrawal clears that attendee's exact linked not-yet-started table seats, even if a child table has a different audience; show that dependency and do not mistake it for an optional non-private action. Do not let a cascade remove in-progress participation or its required registration/access; exclude those dependencies from the block's affected set. Removing a standalone/child table participation does not cancel event registration or siblings. Preserve the account holder's guests and other group members, audit attribution, and history; use existing per-person withdrawal, queue/capacity processing, and safe notifications. Future group acceptance remains atomic.

Automatically removed participation no longer supplies ordinary live chat/address/resource access; independently authorized staff/organizer or retained historical reads remain governed by their existing separate rules. Unselected non-private items, independent guest participation, and in-progress or unaffected third-party private participation retain their normal rules. Do not reuse a new-admission block check as a live-access veto on retained in-progress participation. Ordinary non-private/shared participation may arise later through permitted routes, but old invitations or prior participation never bypass private host/participant exclusion. Recheck actual current state, hosting, audience, permissions, and dependent scope at confirmation; material changes require a refreshed preview before committing. Existing matches and co-host identity edge cases remain separate Q-010 work.

### DM reports and selected evidence

Accepted: the reporter selects individual messages. Authorized reviewers see those messages plus gaps between consecutive selections: the number of omitted messages and the sender identity and character length of **each** omitted message. Omitted bodies remain private. This reveals the extent of missing context without granting access to its contents.

Recommended physical structure, using parent prefixes:

| Proposed table | Fields and invariant |
| --- | --- |
| `direct_conversation_reports` | Tenant/conversation, reporter participant, reason, `status` (default `submitted`; initially submitted/under_review/resolved), submitted time, stable snapshot boundary, client submission key; `resolution_notes` nullable until resolution, required and nonblank when resolved. Proposed lifecycle attribution fields: `acknowledged_at`, `acknowledged_by_user_id`, `resolved_at`, `resolved_by_user_id`; standard audit fields also apply. Permanent retention; reporter and same-tenant staff with `can_handle_reports` may read |
| `direct_conversation_report_messages` | Report FK plus matching tenant/conversation; selected source message ID and sequence, author main user ID, original-text snapshot at submission independent of personal hiding; unique report/message; evidence immutable after submission |
| `direct_conversation_report_gaps` | Report FK, preceding/following selected-message anchors in source order, actual omitted-message count; only intervals with omitted messages between consecutive selections |
| `direct_conversation_report_gap_messages` | Gap FK plus matching report/tenant/conversation, source message ID/sequence, author main user ID, character count; one row per omitted message, **no body or body-fetch entitlement** |

A trusted submission command accepts selected IDs, verifies at least one readable message and that all selections belong to the reporter's same authorized conversation, orders/deduplicates them, and captures one consistent server snapshot. The server computes gaps and their per-message metadata; clients cannot supply or omit gap entries, author identities, or counts. Gap counts equal actual omitted rows, not sequence subtraction. No gap exposes preceding/following conversation content outside the selected interval or messages sent after the snapshot. A single selected message therefore has no between-selection gap; describe this limit in review UI.

Recommend defining character length as Unicode code points in the stored plain-text body at the snapshot, consistently in server code and UI; emoji sequences may count as multiple code points. Personal hiding does not change original-text snapshots or omitted-message lengths/counts; compute evidence from retained canonical messages rather than the reporter's filtered chat display. Review UI can resolve a safe community display label alongside stable sender IDs, without exposing global account details or another community's profile.

Validate all report, selected-message, gap-anchor, and gap-message relationships with matching tenant/conversation FKs and trusted commands. Gap items cannot be promoted to body access by following source IDs or joins. Evidence snapshots are separate from mutable status and resolution notes; chat hide/unhide actions must not rewrite submitted evidence. Report records and related data, including selected evidence, gap metadata, notes, and lifecycle attribution, never expire or disappear. No TTL, purge, soft-delete, or parent/account deletion cascade may remove them. Ordinary DM history now has no automatic expiry under D-096; permanent report-evidence preservation remains an independent requirement. Authorized reporting/blocking should remain usable from retained read-only history (recommendation); neither operation sends a conversation message.

### Report access, retention, and lifecycle — accepted

Add `tenant_staff_assignments.can_handle_reports`, boolean not null. Follow the existing staff-permission invariant: default false for non-owner staff; initialize/backfill and enforce true for owners. An active staff assignment with this flag may view and handle reports only in that assignment's tenant. Staff need no membership in the reported conversation. Active non-owner staff require an active community account under D-105; owners remain exempt. The authenticated submitting user may view their own report, its evidence, current status, and resolution notes without this staff flag. Report ownership is a separate read authorization from current eligibility to send DMs. Other conversation participants or reported users gain no report access merely through being involved.

`can_handle_reports` grants report viewing, acknowledgment, and closure. It grants no access to omitted message bodies or the full source conversation and no authority to hide chat messages for others, delete evidence, or discipline accounts. Event/table message moderation requires community-public audience and the corresponding management permission; private event/table chats and DMs have no staff shared hiding or inspection override. Disciplinary actions retain their separate permissions. Report ownership alone permits no staff lifecycle changes. Permission checks apply to report lists, details, child evidence, API calls, and Realtime; losing a staff grant removes that staff access but never deletes the records, and an independent submitter read grant still applies.

| Lifecycle step | Manual action and persisted result |
| --- | --- |
| Submission | Trusted submission initializes `status = submitted`; clients cannot choose an already-reviewed status or supply staff attribution |
| Acknowledgment | Staff with `can_handle_reports` uses **Acknowledge Report**: `submitted` → `under_review`. Persist trusted acknowledging actor/time. This communicates that staff have seen the report; it does not itself impose a sanction or claim an investigation is complete |
| Resolution | Staff with `can_handle_reports` uses **Close Report**: `under_review` → `resolved`. Save required, nonblank `resolution_notes` and trusted resolving actor/time atomically with the status change |

Viewing a report does not automatically acknowledge it. Age, inactivity, and opening/closing UI screens trigger no lifecycle changes. Resolution does not remove the report, evidence, or notes; authorized staff and the submitter can continue to find resolved reports through status filters. The initial documented flow is submitted → under_review → resolved; further transitions or editing a completed resolution require a separate feature decision. The two actions may be performed by different authorized staff users. Proposed acknowledging/resolving actor fields reference global `user_accounts`, preserving historical attribution and the owner exception to community-account requirements; actor/time fields are unset until their transition and supplied only by trusted code. Each controlled command rechecks permission and current state, preserves earlier evidence/attribution, rejects forged actors and empty closure notes, and handles retries/concurrent actions without duplicate transitions or overwriting a completed resolution.
