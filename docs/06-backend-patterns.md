# Backend code patterns

Status: proposed standards and command contracts; unresolved operating rules remain in the decision register.

## Execution boundaries

Use caller-scoped Data API reads and narrow permitted edits. Seat confirmation, group edits, cancellation, manager decisions, competition confirmation, and admin corrections use database transactions. Derive the actor from verified identity, not request parameters; check live tenant standing, resource participation, and operation-specific permission. Payments and paid memberships are deferred: do not query entitlements or require payment verification for current functionality.

Global search filters out the other account for either viewer before returning results; global matchmaking must not propose or commit a match containing both users. The restriction is between the pair, not a global opt-out for either account. New direct invitations fail when sender and recipient have a block in either direction, even if recipient invitations are enabled. Preserve the existing bilateral DM send/create gate and authorized history.

Do not add a generic personal-block gate to community joining or unrelated shared participation. Preserve guest registrations/seats, booking/group links, queue position, and ordinary processing when removing an account holder's own participation. A sponsor's block relationship neither cancels guest participation nor makes the sponsor's attendance a prerequisite. Revalidate live state before commit and invalidate stale candidates/caches; client-only filtering or a check only at request creation is insufficient. A block confirms only with D-118's mandatory private participation removals and invitation rejections applied within D-119's not-yet-started scope. ### Disciplinary removal and independent staff revocation

A removal preview/command requires effective active same-tenant `can_remove_users` and rejects the owner as a target. Account removal requires both `can_remove_users` and `can_revoke_staff` on the same effective active same-tenant actor when the target assignment is active or paused. No assignment or already revoked status requires only `can_remove_users`. Serialize the target-state lookup with staff creation/resumption/reappointment and recheck actor grants in the removal transaction. Missing either required flag rejects the entire command before any account, staff, booking, resource, audit-transition, or outbox effect. Both paths preserve audit identity; retained revoked grants confer no authority.

Removal atomically sets removed/inactive, revokes active/paused staff, withdraws queued/confirmed personal bookings at not-yet-started gatherings, and cancels not-yet-started unofficial gatherings organized/hosted by the target. Preserve rows and actor/time/reason; event-registration withdrawal clears only the exact attendee's linked table seats. Recalculate capacity and promote whole fitting groups under existing rules. Keep other members of mixed groups and unselected guests intact. Existing guest requests must not be silently rejected solely because their booker was removed; new booking creation remains denied. Explicit guest cancellations are limited to that target's bookings selected in the confirmed removal command under `can_remove_users`, never unrelated booking edits.

Official gatherings must be excluded from automatic organizer cancellation and from cancellation suggestions in the removal preview. Other staff with `can_manage_official_events` continue managing them without depending on the removed organizer's account state; any later cancellation is a separate authorized action. Still withdraw the removed user's personal upcoming seats at official gatherings. D-110 resolves the mixed-sponsorship edge: attached tables derive classification from the event, so an unofficial parent has only unofficial tables and an official parent only official tables. Use this effective classification in the preview and committed removal; preserve both the parent cascade and official exemption.

Use trusted start times: in-progress gatherings and their ongoing reservations are excluded from automatic cancellation/withdrawal. Removed ordinary live participation/chat/address authority ends immediately; any manager action on ongoing bookings uses its own authorization. Retain completed attendance/history and the established historical-read predicates. Parent cancellation preserves booking statuses independently of explicit personal/selected-guest withdrawals.

Confirm against a server-derived affected set. Respect existing private-view scope in preview data, never return private addresses/chat bodies merely through removal authority, and require renewed confirmation for material scope changes. Lock account/staff/resource/booking state in a consistent order, recheck actor authority and owner protections, and serialize removal against resumption/reappointment, new bookings/sends, sponsorship changes, and start-time updates. ## Event/table rules — confirmed 2026-10-12

Events and tables are distinct resources; see the [schema direction](03-database-schema.md#events-tables-locations-and-seats). An attached table belongs to the same tenant. Unofficial event-table creation/linking requires organizer authority; `can_manage_community_events` adds cancellation/archival authority for community-public unofficial resources and D-092 community-public chat moderation; it does not grant event-table creation/linking authority. Official event/table creation and management require `can_manage_official_events`. D-110 requires attached tables to derive official/unofficial classification from their same-tenant event, with no local override; only standalone tables store their own classification. All creation, management, moderation, and removal checks resolve that trusted value rather than trusting a request field or inferring it from the host's staff role. Keep public/private audience checks separate.

Enforce the standalone/attached storage shape and tenant FK in the database; an attached table must not contain a separate sponsorship value. Return effective classification through authorized projections without leaking private parent fields. Any later attach/detach/move or event-reclassification command must recheck current and resulting authority and registration compatibility under coordinated locks; do not permit a relation or sponsorship update to bypass official-management permission. No new reassignment workflow is introduced by this rule.

Published community events have visitor-readable safe summaries. New participation and guest booking require an active tenant and active, approved, non-banned community accounts; existing guests survive voluntary sponsor deactivation under D-098 and disciplinary removal unless explicitly selected for cancellation under D-108; private audience checks still apply. Use one event registration per attendee and one table participation per person, with booking responsibility separate from attendance. Guest names are optional; a sponsor may register only guests without attending or occupying a seat.

Event-table participations reference each occupant's exact approved registration in that event and tenant. Standalone participations store attendee account/optional guest name directly. Cancelling a registration releases only its linked table reservations; explicit group cancellation covers the selected registrations and linked seats. Withdrawn/rejected/cancelled requests cannot be automatically restored by a retry or promotion worker.

New guest bookings and resubmissions require `allow_guests = true`; disabling it leaves existing requested/waitlisted/confirmed bookings unchanged. Serialize flag edits and booking creation on the table. Optional guest-removal controls call a separate authorized cancellation command for selected table participations, preserving event registrations and other-table bookings. Cancel the selected rows transactionally and re-evaluate the remaining group under the current confirmation mode. Neither private-view permission nor unofficial-resource cancellation/archive moderation grants table-management authority. D-108 separately permits selected target-owned guest cancellations through the can_remove_users removal command, without granting general table management.

### Confirmation modes and group transactions

`tables.manually_confirm_seats` is non-null and defaults false. When false, process requests immediately and automatically confirm eligible, non-withdrawn whole groups that fit; re-run allocation when capacity/eligibility changes. When true, only an authorized table manager may approve a queued request. The manager may select requests for approval/rejection or notify the booking account of an issue at their discretion; FIFO does not force a manual decision. Approval directly confirms the group with no further action by the booking account.

Every confirmation loads the full persisted group/revision, locks the table and relevant registrations, checks the table and parent event lifecycle, current mode and actor authority, standing, exact event/tenant links, applicable guest rules, and full capacity, then confirms all people or none. Serializing confirmation with group edits, withdrawal, rejection, mode changes, and resource cancellation prevents stale approvals. Manual approval cannot exceed capacity or bypass event registration. A client loop of per-person RPC calls does not satisfy atomic acceptance.

After the manager chooses Continue in the manual-to-automatic confirmation modal, an authorized command sets `manually_confirm_seats = false` and processes already queued requests using the standard automatic allocator. Proposed transaction contract: serialize the setting change and initial queue pass with other seat/mode/group changes, preserve current queue order, and confirm eligible whole groups that fit, recalculating capacity after each group. Skip non-fitting groups without resetting their priority; never restore withdrawn/rejected requests or let a concurrent new request bypass an older fitting group. Commit the setting, resulting confirmations, and durable notifications together; failure before commit leaves the setting and queue unchanged. Retries return the committed outcome without duplicate confirmations/notices. Cancel or dismissal before submission sends no mutation command and leaves manual mode enabled.

Current states are requested/waitlisted/confirmed/rejected/cancelled; exact display mapping can distinguish awaiting manager review from waiting for capacity. Pending rows consume no capacity. Only confirmed participations consume table seats, one per person. Event attendance capacity is separate. No initial offered state, seat-claim endpoint, response deadline, reservation-expiry worker, payment hold, or payment-pending state is needed.

### Queue allocation and pending-group edits

Automatic allocation is first-come, first-served among eligible whole requests that fit. Under the capacity lock, scan server-assigned queue order with a stable tie-breaker; skip a group that does not fit without resetting its position, confirm the earliest one that does, recalculate capacity, and continue. New instant requests cannot bypass an older eligible fitting request. Concurrent allocators must share this ordering/locking protocol. On a manual table, capacity changes refresh the queue but do not confirm anyone without a manager decision.

Keep queue priority for optional guest-name edits and removals from a waiting group. Additions reset the enlarged group's queue timestamp to the new submission time; the UI explains this before saving. Apply edits and request-revision updates atomically, revalidate eligibility and new-guest restrictions, and reject stale decision payloads. Removing all people withdraws the request. Pending-group edits do not imply splitting a group during confirmation.

Use durable submission/idempotency keys so retries return the existing outcome rather than duplicate unnamed guests, issue duplicate notices, or restore a terminal request. Explicit resubmission after rejection/cancellation gets a fresh queue timestamp and request revision; preserve prior decision history. If recipient-confirmed offers are introduced later, group edits must also invalidate/revalidate their reserved capacity and prevent claiming an old group; no such offer flow ships now.

### Manager decisions and notifications

Approving a manual request confirms the entire current group. Rejecting it marks all its participations rejected and removes it from active queue queries entirely; it can never be promoted without an explicit new submission. Keep immutable decision history for the affected request/group revision, including server timestamp, rejecting global user, and optional reason. Keeping historical rows is not keeping the rejected request in the queue.

The booking account receives prompt approval/rejection notifications after commit. A rejection notice includes decision timestamp, rejecting user's safe display identity, and the reason when supplied; do not expose staff email/private profile fields. Persist the decision and in-app notification in the same transaction, and queue any external delivery through a deduplicated outbox. Publish only committed outcomes, with retries after delivery failure; external channel/transport latency is not a reason to delay the in-app decision.

An issue-notification action sends a resource-scoped notice to the booking account while leaving the request queued. It creates no response timer, automatic rejection, or automatic DM conversation. Community DMs are a separate MVP capability. An explicit manager rejection differs from notifying about an issue.

### Invitations, oversight, and cancellation

New private invitations check the recipient's `allow_private_invitations` preference (default true), the bilateral sender/recipient block, and D-118's private host/participant exclusion. A third-party sender cannot invite a blocked counterpart into the host's private event/table. Disabling the preference affects new invitations only, but confirming a block automatically rejects pending invitations for the affected private host/actual-participant relationships in not-yet-started resources under D-119; in-progress invitations are not automatically rejected. Manual decline/revocation in the block dialog is reserved for not-yet-started non-private resources. Later admission rechecks the same private gate; invitation expiry remains independent of the removed seat-offer/response window.

Replace the proposed `can_manage_events` with `can_manage_community_events` and `can_manage_official_events`, both default false for non-owner staff and true for owners. The community flag permits cancellation/archival of unofficial community-public events/tables and shared message hide/unhide/View Message for their community-public chats, without other resource-data edits. The official flag is required for official-resource creation/management and corresponding community-public chat moderation. Private event/table chats have no staff shared moderation or inspection override; public moderation reads use the matching staff flag. `can_see_private_events` permits scoped private event/invitation/table/chat reads, including eligible private archives, without chat sends, address reads, or writes. A qualifying organizer/historical relationship can independently grant history reads. Participant-permission grants remain under `can_manage_community_permissions`; staff-permission edits remain owner-only.

### Event cancellation and archive commands

Apply the same cancellation/archive protocol to events and tables. No hard delete or initial reopening/unarchive command exists. Authorize unofficial community-public cancellation/archival against organizer status or `can_manage_community_events`; private organizers manage their own unofficial resources without granting staff write access through private-view permission. Official create/edit/cancel/archive commands require staff with `can_manage_official_events`. Check live resource classification and authorization, not a client-supplied official/unofficial flag.

Cancel the resource and record server timestamp, initiating global user, optional reason, and whether it had any registration/participation rows of any status. Event cancellation also sets attached tables to `cancelled`, leaving already-archived tables archived. Persist parent/child transitions and required notifications together without updating any registration/participation rows. An independent table cancellation/archive cannot alter its event or siblings. Newly cancelled children receive their own actual cancellation metadata and booking snapshot; existing cancellation history and archive metadata remain intact. Serialize the event and table transitions with child creation/linking, booking, approval, and allocation so concurrent work cannot escape the cascade or confirm after cancellation. Reject new attachments to cancelled/archived events. Suppress new registrations/invitations/acceptance, bookings, promotions, allocation-triggering mode switches, and obsolete reminders; never fabricate attendance/no-shows.

A directly requested Archive action requires an authorized actor and a cancelled resource with either zero booking rows at cancellation or at least 30 continuous cancelled days. Previously rejected/withdrawn rows count. Use server time and the protected snapshot; retries cannot reset timestamps or rewrite cancellation metadata. Archiving the parent event sets all attached table statuses to `archived` in the same transaction, without separate table-manager actions or a second child wait period. The event action's authority applies to this dependent cascade only and does not grant unrelated table-editing permissions. Preserve already-archived children and all per-person rows. Independently requested table archival still checks that table's own authorization and eligibility. Cancellation never downgrades an archived child.

Persist the parent-to-child lifecycle cascade and continue checking both statuses defensively in participation commands. Derive history reads separately using the [accepted audience rules](03-database-schema.md#cancellation-and-archive-visibility): a past registration/participation in any state grants scoped history access; guest rows grant it to their booker, never a new guest identity. Former unofficial organizers and authorized staff retain access too. Public listings/invites must not expose unrelated archived resources or chat. Parent archive filtering must preserve a qualifying child history without returning unauthorized parent details or other child tables.

Cancellation immediately denies sends to the affected event/table chats and participant-based exact-address reads, even while participation status remains confirmed. Eligible historical viewers retain read-only cancelled/archived chat indefinitely; no archive-age cleanup may erase this promised history. Do not use a single current-participation predicate for reads, sends, and addresses. Preserve the authenticated organizer's existing location-management access where applicable after cancellation/archival. This is an independent, location-scoped authorization; it is not supplied by either management flag or the private-view flag. Add no general staff exception or external venue/guest identity.

### Cancellation notification policy

Accepted in full on 2026-10-13: an in-app notice reaches users with queued/confirmed bookings and the additional affected recipients below. Historical access and notification eligibility are separate: retaining a row does not always trigger a new alert. The following routing, aggregation, content, archival, and delivery behavior is confirmed policy:

| Recipient situation | Required notification behavior |
| --- | --- |
| Queued/confirmed account-holder booking | Notify the account holder once for the affected cancellation, regardless of automatic/manual mode. |
| Queued/confirmed guest booking | Notify `booked_by_user_id`; aggregate their own booking and guest rows into one notice. Never attempt guest delivery or require names/contact details. |
| Only withdrawn/cancelled/rejected historical rows | Preserve archive/chat access, but send no new cancellation alert solely for those rows. A separate organizer/invitation role can still qualify. |
| Organizer or affected child-table host without a booking | Notify them too, especially when staff cancels their resource or an event makes their table unavailable. |
| Pending actionable invitation | Send one cancellation notice, explaining that acceptance is no longer available. Do not alert recipients solely for declined, revoked, or expired invitations. |
| Staff with no affected booking/organizer/invitation role | No broadcast to all staff; management audit access is separate from personal notifications. |

For an event cancellation, form one recipient union across eligible event registrations, affected child-table bookings/hosts, organizers, and actionable invitations. Send at most one notice per global user for that parent cancellation, summarizing their affected tables and party size where relevant. Do not fan out additional notices for child status transitions within that same parent action: use the parent cancellation identity for deduplication. A separately initiated table cancellation uses its own identity; retrying cancellation of an already-cancelled table does not generate another notice. A user's own cancellation action produces its normal success feedback; if that user also qualifies as a recipient, deduplicate their inbox entry in the same way.

Each notice includes community and event/table title, scheduled date/time, cancelled status, cancellation timestamp, cancelling user's safe display name, optional reason, and an authorized details link. Include a concise booking summary such as 'Your booking for you and two guests is affected'; do not include other users' guest lists, exact addresses, or chat previews. Keep cancellation attribution as a snapshot independent of later archive updates; human actors are not replaced with system attribution merely because a worker delivers the notice.

Send no additional notification solely for archival: it changes where the record appears without changing the already-cancelled gathering. Keep the cancellation notice in the recipient's inbox. Historical registrants/participants, guest bookers, and eligible organizers/staff can follow it into permitted archived details/chat. An invitation-only recipient may retain the minimal notice but cannot use it to bypass archived-resource access rules.

Delivery contract: capture recipient IDs and notice data with the committed cancellation and use a unique cancellation/recipient key, with durable outbox retries. Cancelling concurrently with registration must produce one coherent result: a booking committed before cancellation is included; a later attempt is rejected. A retry neither duplicates notices nor restarts the archive clock. Suppress obsolete queued reminders; workers recheck effective resource lifecycle before delivery. Recheck link authorization when opened rather than embedding private payloads. In-app notices are the initial channel; email/push remain a separate deferred delivery decision.

## Seat state machine — current direction

| Operation | Transition / check |
| --- | --- |
| Automatic request or queue promotion | On `manually_confirm_seats = false`, eligible current whole group → confirmed immediately if its queue order and full capacity permit; otherwise remain queued without deadline |
| Manual request | On `manually_confirm_seats = true`, persist group for manager review; no seats consumed |
| Manual → automatic | Manager's Continue authorizes submission; server checks table-management authority, switches to false, and processes the existing queue in receipt order among eligible whole groups that fit. Cancel before submission leaves true and performs no queue processing |
| Manager approves | Current queued group → confirmed atomically if authorized, eligible, and all seats fit; no booker reconfirmation |
| Manager rejects | Current queued group → rejected in full; remove from active queue and notify booker with timestamp/actor/optional reason |
| Manager notifies about an issue | Request remains queued; send scoped notice without response deadline or automatic state transition |
| Edit guest name / shrink waiting group | Preserve priority, revise group atomically, re-evaluate under the current mode |
| Enlarge waiting group | Revalidate all added people; reset queue timestamp for the enlarged group after explaining the effect |
| Withdraw / cancel | Cancel selected people or explicit whole request; release confirmed seats and re-run automatic allocation where applicable |
| Event attendance cancelled | Cancel the person's registration and linked table participations; preserve history |
| Event/table cancelled | Preserve all per-person rows; event cancellation sets attached tables cancelled except already-archived tables. Record transitions, preserve earlier cancellation history, and notify the accepted recipient set once per user. Deny participation actions/sends/participant addresses while preserving authorized historical reads |
| Cancelled event/table archived | Direct action checks authority and zero-booking/30-day eligibility. Parent-event archival sets every attached table archived in the same operation. Preserve per-person rows, cancellation history, authorized visibility, and indefinite read-only chat; no archive-only alert |

Conceptual commands include create_event, register_for_event, create_table, request_seats, edit_pending_group, confirm_eligible_groups, approve_table_request, reject_table_request, notify_table_request_issue, cancel_participation, cancel_event, cancel_table, archive_event, and archive_table. These are examples, not final SQL signatures. Commands operate on persisted request/group revisions, not arbitrary subsets chosen for approval.

## Address, chat, and content

Address retrieval checks participant access independently from existing organizer/location-management authority, tenant/standing restrictions, and resource/parent lifecycle. Resource cancellation immediately ends participant-based address access despite retained confirmed rows. Historical/archive/chat access never authorizes exact addresses. Preserve an authenticated organizer's existing location-specific management access after cancellation/archival; do not create or broaden it from organizer status alone. No general staff address exception, external venue account, or new guest identity is introduced. Neither event-management flag nor the private-view flag grants addresses. Keep address tables out of general/history/notification payloads and prevent joins, views, and Realtime from bypassing that boundary.

Event/table messages are stored durably in their respective `event_messages`/`table_messages` tables before delivery. Use the matching parent FK and chat lifecycle record. Active participant chat requires active approved community standing in an active tenant; event chat authorizes its registrants/organizers without requiring table seating; active table chat uses its own participant/host rules. `can_see_private_events` includes private event/table chat reads but no sends or DM access. Event cancellation denies event-chat and affected table-chat sends immediately; independent table cancellation affects only its chat. Authorized resource-specific historical viewers, including guest bookers, retain indefinite archived reads. Validate size and authenticated author, deduplicate retries by tenant/resource/author/client-message ID, and recheck current parent lifecycle so a stale client cannot send after cancellation. Message bodies remain retained; personal hiding and scoped staff moderation affect display without changing source content. Inactive users lose ordinary participant-chat access to still-active gatherings while retaining qualifying cancelled/archived history. Archived communities retain only independently authorized history; indefinite history is not a new posting or moderation permission.

Personal Hide for me/Unhide for me commands derive the viewer from authentication and validate current read access to the exact message/chat. Upsert/delete only that viewer's hide-preference row with matching tenant/parent/message FKs; never accept another viewer ID as authority. Retained read-only viewers may change personal preferences. These writes do not change original text, another user's display, shared moderation state, message chronology, or report evidence. No staff hide-for-everyone or moderator View Message override exists for DMs or private event/table chats. Existing private-view staff read access is retained and grants only ordinary self-view preferences.

Event/table moderator hide/unhide commands first require a community-public parent resource, then active same-tenant staff and the actual resource classification's community/official management flag. Reject private chats regardless of management/private-view permissions, ownership, or participation; keep existing private-chat oversight reads separate. Organizer status, private-view authority alone, and report-handler authority are insufficient. Update the separate moderation row through controlled commands, using a revision/current-state check and idempotent desired-state semantics; record trusted actor/time and safe action metadata in `tenant_admin_actions`. An unhide must not clear users' personal hide rows. Authorized shared visibility changes remain available on cancelled/archived community-public chats without enabling posting or content edits.

View Message is an explicit read of the retained body after the same community-public audience and moderator-permission checks. Private-chat read access never qualifies for this moderator-only preview. It changes neither shared hidden state nor personal preferences and must not emit an unhide/re-hide event. Recommend audit metadata for this sensitive inspection without recording the body. Recheck permissions after revocation and on every preview request; possession of a source message ID grants no access.

Ordinary community-public event/table message projections suppress a body whenever shared moderation hides it; personal filtering applies independently for each viewer. Return safe placeholders so controls remain reachable. Do not expose canonical hidden bodies through direct table grants, alternate queries/joins, quotes/search/notifications, or Realtime row payloads. Restrict raw-body access and deliver sanitized projections plus visibility invalidations. Invalidate cached displayed bodies on moderator changes and re-evaluate current visibility on reconnect/pagination. View Message uses its own authorization path and does not make the body available to ordinary subscribers. Already seen/copied content cannot be recalled. Report submission derives selected text and gap counts from canonical messages, including personally hidden intervening messages; all submitted evidence remains unchanged by hiding.

Use private storage for restricted assets and short-lived authorized access when appropriate. Do not make profile or chat media globally readable by accident. Rate limits and moderation controls should address the selected posting/chat surfaces without treating payment as a trust guarantee.

## Championship result protocol

1. An eligible match participant submits a versioned result with eligible players, scores/placements, date, and applicable rules version.
2. Another participant independently confirms or disputes that exact version. Self-confirmation cannot satisfy the rule; required quorum beyond one other participant remains open.
3. Only confirmed current, nonvoid versions count toward standings.
4. A dispute removes the result from counted standings while unresolved; define dispute deadlines and re-opening rules.
5. Authorized corrections produce a new version and invalidate earlier confirmations. Admin adjudication is explicit and audited.
6. Recompute the standings projection deterministically and finalize finalists/achievements through controlled commands.

Store validated scoring parameters rather than arbitrary code. Lock/freeze the effective rules for accepted results; changing rules requires an explicit version/recalculation policy. Do not hard-code one game's formula throughout UI and SQL.

Nonmember competition access uses entry eligibility, not paid-network entitlement. Qualification need not reference a Meet & Play table. Final location follows the same private-address rules as other official events.

## Message validation and shared rate limits

Apply D-093 to DM, event-chat, and table-chat sends: at most 5,000 characters with line breaks allowed; reject empty/whitespace-only or overlength bodies, never silently truncate. The frontend preserves rejected drafts. Use one documented character-count convention across the API, UI, and report-gap metadata; Unicode code points are recommended.

Enforce 30 messages per minute per main user account across all communities and chat types, plus 10 new DM recipients per hour against the same main-account budget. Recommended rolling-window accounting uses trusted time and atomic reservation/commit or equivalent shared serialization so concurrent tabs, devices, and tenants cannot exceed the limit. Deduplicated retries of successful sends consume no additional quota and create no additional delivery; a failed transaction rolls back successful-send accounting. The schema's recommended new-recipient definition counts a distinct main-account peer on first successful contact, independently of the later per-community request-approval rules. Keep cross-community rate/contact metadata server-only.

Return a stable rate-limited outcome with retry guidance; preserve content and its client idempotency key for a legitimate retry. All send paths, including RPCs and Realtime publication, must go through trusted validation and authorization; publishing directly must not bypass persistent-send limits. Rate limiting does not grant send eligibility or replace consent/standing/block checks.

## Community direct messages — schema and authorization direction

DMs, reports, and blocks are MVP. Both endpoints must have approved accounts in the conversation's community. No conversation spans tenants, and staff identity is no substitute for participation. System notices continue through notifications rather than impersonating a DM participant.

Use general conversation/participant tables with no conversation kind, stored pair identity, pair uniqueness constraint, or database participant-count constraint/trigger. The initial server create-or-get command accepts `tenant_id` and one `recipient_user_id`, derives the sender from authentication, resolves the existing identity-based thread, and validates distinct approved accounts and recipient controls before atomically creating a missing root and both participant records. Returning authorized existing history uses the read predicate, not the new-send predicate. Reject extra recipients and caller-supplied sender/membership overrides at the API boundary. Composite FKs bind participants to same-tenant community accounts, messages to their conversation participant/author, and personal state to its owner. Grants/RLS prevent direct client conversation-creation or membership changes outside authorized commands. No add/remove/replace-participant command is exposed initially. The server command may be a transactional RPC; its one-recipient contract does not imply a database count invariant.

One continuing DM thread per unordered pair of main user identities within a community is accepted (D-095). Personal inbox archival, blocking/unblocking, logout, and rejoining must not generate another thread. Serialize every creation path for the tenant and normalized sender/recipient IDs, then look up the conversation with exactly that participant set before creating one in the same transaction. A transaction-scoped lock followed by a lookup that observes the prior lock holder's committed result, or equivalent serializable handling with retries, is recommended; a preflight SELECT alone is insufficient. Opposite-direction requests must share the same key and global lock order with send/eligibility checks. This is command-level concurrency handling, not a stored pair key or database participant-count limit. Finalize and test the specific locking/isolation strategy during implementation.

Creating a missing conversation only on the first successful send remains a recommendation awaiting a timing decision. If adopted, create the root/participants/message/outbox atomically and leave no empty thread after a failed send. Group features can later create larger memberships through authorized commands while preserving existing message/conversation IDs; define group history, consent, and thread-reuse semantics separately before enabling those operations.

On each creation/send, verify the tenant is active and both accounts are active and approved, the recipient allows DMs, and neither direction has an applicable main-account block. False `allow_direct_messages` prevents incoming messages even in existing threads. Inactive/pending/suspended/removed accounts neither initiate nor receive new messages. Inactive/suspended/removed participants retain read-only history; do not use the send predicate to gate historical reads. Personal opt-out and blocking preserve history. Future sender-community-account request approval is not a current gate.

Serialize conflicting send and standing/opt-out/block changes with a defined lock order or equivalent transactional protection. A send must not commit as authorized using stale eligibility after a restriction took effect; retries recheck authority before creating anything new. Main-account disciplinary identity survives rejoining, including auto-approval checks. Personal blocks apply across all shared communities; disciplinary actions remain limited to their issuing tenant and follow the main account on rejoin. Check the global user pair on every community's DM write. Coordinate concurrent blocks/sends across tenants using that global pair, rather than relying only on a tenant/conversation lock. A community's staff cannot use this identity link to sanction other communities. Neither an owner nor any event/table permission bypasses personal DM controls.

Persist messages with per-sender/conversation client idempotency keys and stable server order; a legitimate retry returns the original message without duplicate delivery. Read cursors must reference the same conversation, advance monotonically, and stay private. Personal inbox archival never changes the peer's history. Plain text is initial; attachments, sender edits/deletion, requests, shared receipts, and typing are deferred. Ordinary DM history has no automatic expiry (D-096): no message TTL or age-based cleanup. Personal archive, hiding, muting, blocking, and community suspension/removal preserve message history and existing authorization. Monitor usage and configured budget thresholds; threshold alerts trigger operational review rather than message deletion. D-097–D-103 settle community departure/archival history; global deactivation/closure/deletion/anonymization remain deferred. DM visibility changes are self-only hide preferences, with no staff shared-hide or inspection override; submitted report records and evidence are permanently retained.

Report submission is a controlled transaction accepting selected message IDs, not client-computed evidence. Verify reporter access to each message in one tenant/conversation; deduplicate/sort selections and capture a consistent server snapshot. Snapshot selected bodies/attribution and compute intervals between consecutive selections. Record every omitted message's sender and character length plus the actual count per gap, with no omitted bodies. Sequence values may have numeric gaps, so count rows rather than subtracting IDs. Bind selected records, gap anchors, and gap items to their report and exact conversation through FKs/checks. Deduplicate submission retries. A single selected message has no between-selection gap; do not imply surrounding context was checked.

Report evidence and mutable lifecycle state have distinct write rules. Reporters may read their own reports, evidence, status, and resolution notes. Active same-tenant staff with `can_handle_reports` may read and handle reports without conversation membership; non-owner staff require active same-tenant community accounts, while owners remain exempt; default false for non-owner staff, always true for owners. The flag grants no full-conversation/omitted-body reads, shared chat-hiding authority, or account discipline. Submitted evidence remains immutable, and all report records/related data are retained permanently with no expiry, purge, or deletion cascades. Personal/shared chat hiding and ordinary DM retention without automatic expiry preserve report snapshots under their independent permanent-evidence rule. Revoked staff access is denied while independent reporter access remains valid. Recommend that reporting/blocking remain available to users with retained read-only history.

Submission always initializes `status = submitted`. A controlled Acknowledge Report command manually changes submitted → under_review and records authenticated staff actor/time; merely reading a report does nothing. A controlled Close Report command manually changes under_review → resolved, requiring nonblank `resolution_notes` saved atomically with resolving actor/time. Both require current same-tenant `can_handle_reports`. Lock/check current state, preserve earlier attribution and evidence, and prevent direct writes from forging status/notes/actors. Retry handling must not repeat transitions or overwrite the first committed resolution; concurrent conflicting changes return a stale-state outcome. No time-based lifecycle transitions, automatic report deletion on resolution, or implicit sanction occurs. Record staff actions in `tenant_admin_actions` while exposing authorized report lifecycle details through the report record rather than granting audit-log access.

Authorize Realtime reads/subscriptions per tenant/conversation, including after reconnect and account changes. Restriction changes invalidate send eligibility without discarding authorized history. Reports use their own restricted delivery scope; no omitted body or unauthorized case material goes onto a conversation/public channel.

D-094 settles initial DM alerts: in-app, enabled by default, containing community, sender, unread count, and authorized link without a body preview; email/push remain deferred. Committed sends feed durable outbox work. Reconcile at most one active unread notice per recipient/conversation using an atomic upsert or equivalent uniqueness guard, and derive counts from current read state so retries/out-of-order jobs cannot inflate them. Read cursors remain self-only and monotonic. Focus alone is insufficient: suppress an additional alert for a new message actually displayed in the focused conversation, not one in a background tab or beyond the user's current reading position. Reconcile read acknowledgments with pending notification work.

Persist private per-conversation `is_muted = false` by default in the user's conversation state. Muting lasts until manually changed and does not stop message storage/delivery. Suppress notification-inbox entries, toasts, sounds, and main notification badge contributions while keeping conversation-list unread state. The same peer's other-community thread is independent. Recommended reconciliation suppresses an active unread DM notice and invalidates pending work when muted; unmute alone neither restores it nor schedules backlog alerts. A subsequent eligible message can produce one notice with the current unread count. Use notification eligibility generations/watermarks or equivalent cancellation of stale work so a delayed pre-mute job cannot alert after unmute. Recheck access, read state, and mute eligibility before delivery. Personal hides and receipt opt-out/blocking remain separate controls. See the [remaining messaging questions](03-database-schema.md#messaging-policy-decisions-before-implementation).

## Reliable work and notifications

Write a notification/outbox record in the same transaction as a seat offer, request decision, or other important committed state. A worker delivers/retries with deduplication, backoff, and monitoring. A delivery failure must not roll back a valid seat or fabricate delivery success.

Automatic queue allocation must run promptly when requests, eligibility, or capacity change, with durable retry if asynchronous work is needed. There is no current waitlist-offer expiry or expired-claim worker. Chat archival and invitation expiry remain separate lifecycle concerns. The in-app inbox carries committed decisions immediately; external email/push choices remain open.
